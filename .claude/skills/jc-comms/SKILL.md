# jc-comms

한국 B2B·MICE 프로젝트 운영 현실의 **내부/대외 커뮤니케이션 글쓰기** 스킬. 발주처·사무국·협력사·참가자·스폰서 사이에서 매주·매행사 오가는 짧은 글(주간 업데이트·소식지·문의 응답·상태/인시던트/리더십/프로젝트 보고)을, 정해진 양식·길이·톤으로 빠르게 초안화한다.

원본 프리셋 `internal-comms`의 4종 양식 골격(포맷·길이·체크리스트)을 그대로 유지하되, 미국 테크 기업 사내 커뮤니케이션 맥락을 **한국 MICE PCO/PEO 운영 맥락**으로 번안했다.

## 1. 본 스킬이 다루는 것 / 다루지 않는 것

### 다루는 것 (DO)
- **3P 주간 업데이트**(Progress/Plans/Problems) — 행사 프로젝트의 주간 진척을 발주처·사무국·협력사·리더십에게 30~60초 분량으로 보고
- **뉴스레터** — 팀/사무국 소식·시즌 행사 안내를 불릿 묶음으로 정리(Slack·메일 배포용)
- **FAQ** — 발주처/참가자/스폰서가 반복하는 문의를 모아 표준 응답 작성
- **일반 커뮤니케이션** — 위 3종에 안 맞는 모든 것: 상태 보고·인시던트(장애·사고) 보고·리더십 업데이트·프로젝트 업데이트·내부 공지·대외 안내문
- **외부 송부용 / 내부 보관용 톤 분기** (§4) — 같은 내용을 발주처 송부 톤과 내부 솔직 톤으로 갈라쓴다
- 시각 요약(HTML 카드 등)이 필요하면 **jc-design-system 시그니처 토큰** 적용 (§5)
- 초안 완성 후 **jc-redteam 3축 검증**으로 납품 전 최종 점검 연결 (§6)

### 다루지 않는 것 (DON'T)
- 회의 transcript 구조화·8축 추출·Action Items·회의록 대시보드 → **mice-meeting-minutes**
- 비딩/수주 제안서·PT 자료 → **mice-proposal**
- 발표 대본·MC 멘트·사회자 진행 스크립트 → **pt-script**
- 견적서·산출내역서 → **mice-estimate**
- 스폰서·협찬 유치 영업 데크 → **mice-sponsor-deck**
- 행사 결과 KPI 분석 대시보드 → **mice-dashboard**
- 완성된 결론·문서의 적대적 검증·정밀 감수 → **jc-redteam** (본 스킬은 *쓰기*, redteam은 *공격*)

> **경계 한 줄 요약**: 본 스킬은 **짧은 커뮤니케이션 글을 *쓴다***. 긴 산출물(제안서·대본·견적·대시보드)을 만들거나, 입력 문서를 분석하거나, 완성물을 검증하는 일은 형제 스킬 몫이다.

## 3. 표준 워크플로우

작성할 커뮤니케이션의 종류를 먼저 정하고, 해당 가이드를 로드해 그 안의 포맷·톤·수집 지침을 따른다.

```
[요청 입력: "무엇을, 누구에게"]
    ↓
1. 커뮤니케이션 종류 판별 (3P / 뉴스레터 / FAQ / 일반)
    ↓
2. 해당 가이드 로드:
     references/3p-updates.md         — 행사 프로젝트 주간 Progress/Plans/Problems
     references/event-newsletter.md   — 팀·사무국 소식 / 시즌 행사 안내
     references/faq-answers.md        — 발주처·참가자·스폰서 문의 응답
     references/general-comms.md      — 상태·인시던트·리더십·프로젝트 보고 등 그 외 전부
    ↓
3. 대상·범위 확정 (발주처/사무국/협력사/참가자/스폰서 + 기간) → 외부 vs 내부 톤 결정 (§4)
    ↓
4. 정보 수집 (사용자 제공 자료 / Slack·메일·Drive·캘린더 접근 시 활용 / 부족하면 질문)
    ↓
5. 가이드 포맷대로 초안 작성 — 회사·실명·발주처는 외부 주입 변수로 (§7)
    ↓
6. (선택) 시각 요약 필요 시 jc-design-system 토큰 적용 (§5)
    ↓
7. (권장) jc-redteam 3축 검증으로 납품 전 최종 점검 (§6)
```

종류가 어느 가이드에도 맞지 않으면 `general-comms.md`로 처리하거나, 원하는 포맷을 사용자에게 한 번 묻는다.

### 정보 수집 도구 (접근 가능 시)
- **Slack**: 반응·답글 많은 팀/공지 채널 글 — 진척·이슈 신호
- **Google Drive / 문서**: 조회수 높은 핵심 문서(운영계획·진행상황·결과보고)
- **메일**: 회신·내용 많은 발주처/협력사 스레드
- **캘린더**: 킥오프·발주처 정기협의·현장 점검·리허설 등 비반복 핵심 일정

→ 접근 권한이 없으면 사용자에게 커버할 항목을 직접 받는다(이 경우 본 스킬은 주로 *포맷팅* 역할).

## 4. 외부 송부용 vs 내부 보관용 톤 분기

같은 사실도 **받는 사람**에 따라 톤·노출 수위가 다르다. 모든 가이드는 이 두 톤을 지원한다.

| 구분 | 외부 송부용 (`--external`) | 내부 보관용 (`--internal`) |
|------|--------------------------|---------------------------|
| 대상 | 발주처·참가자·스폰서·외부 협력사 | 사무국·내부 팀·리더십 |
| 톤 | 정중·사실 위주·완결된 문장 | 솔직·직설·핵심만 |
| 리스크/문제 | 영향+대응책 중심, 책임 공방 배제 | 원인·내부 사정·솔직한 평가 포함 |
| 금액·마진·내부 일정 | 비공식 수치 비노출("별도 공유 예정") | 그대로 기재 가능 |
| 실명·제3자 평가 | 역할명("발주처 담당자")·완곡 | 실명·직함 허용 |

- **기본값**: 발주처/참가자/스폰서 대상 = 외부 톤, 사무국/내부 보고 = 내부 톤.
- 외부 송부 글에서 한 줄을 잘못 남기면 분쟁이 길게 가지만, 한 줄 더 보수적으로 가는 비용은 작다 — **모호하면 외부 톤(보수적)으로 기운다.**
- 민감 발언 마스킹의 더 세밀한 카테고리·판정이 필요하면 `mice-meeting-minutes/references/redaction-rules.md`의 5종 카테고리를 참조한다(본 스킬은 그 요지만 적용).

## 5. 디자인 적용 (시각 요약이 필요할 때만)

대부분의 산출물은 **텍스트**(Slack·메일 붙여넣기용)다. 별도 요청으로 시각 요약(HTML 카드·상태 보드·인시던트 타임라인 등)을 만들 때만 디자인을 입힌다.

- 시각 산출 직전 `jc-design-system`의 `references/signature-tokens.md §6 JSON`을 로드해 시그니처 토큰을 적용한다. **색·폰트·사이즈 값을 본문/코드에 박지 않고 SoT에서 읽는다**(미러 금지).
- 클라이언트가 지정되면 `client-overlays.md` 오버레이(primary/accent/logo 3토큰)를 함께 적용, 미지정이면 `personal`(시그니처 그대로).
- 적용 영역 매핑(권장):

| 영역 | 토큰 |
|------|------|
| 헤더 띠 | `color.primary` (Deep Navy) |
| 강조·CTA·링크 | `color.accent` (Electric Blue) |
| Progress·완료·확정 | `color.success` 본문이면 `successStrong` (WCAG AA) |
| Plans·예정 | `color.accent` |
| Problems·인시던트·경고 | `color.point.orange` / 심각 시 `color.danger` |
| 차단·최우선 마커 | `color.point.magenta` |

- 폰트는 어떤 경우에도 시그니처 고정: Pretendard(한글)/Inter(영문)/JetBrains Mono(숫자).
- 공통 룰(인라인 리마인더 + 정본 링크):
  - `RULE-WCAG` — 본문 대비 4.5:1↑. 정본: `jc-design-system/references/shared-rules.md#RULE-WCAG`
  - `RULE-PRINT-LIGHT` — 다크 HTML도 인쇄 시 라이트 강제. 정본: `…/shared-rules.md#RULE-PRINT-LIGHT`
  - `RULE-NO-COMPANY` — §7. 정본: `…/shared-rules.md#RULE-NO-COMPANY`

> PPTX는 본 스킬 산출물이 아니므로 `RULE-PPTX-HEX`는 적용 대상 아님(HTML/CSS는 `#` 포함 hex 사용).

## 6. 생태계 연결 — 초안 검증 (jc-redteam)

커뮤니케이션 글, 특히 **외부 송부용**(발주처 안내문·인시던트 보고·리더십 업데이트)은 발송 전 결함이 곧 신뢰 손상이다. 초안 완성 후 `jc-redteam`의 **3축 검증**으로 점검한다.

| 축 | 본 스킬 산출물에서 보는 것 |
|----|--------------------------|
| **내용 검증** | 사실·숫자·일정의 정확성, 책임 소재 표현이 분쟁을 부르지 않는지, 누락된 영향/대응책 |
| **오탈자 감수** | 맞춤법·용어 일관성·비문, **날짜·금액·KPI 수치 오류**, 고유명사 |
| **대안 제시** | 더 나은 프레이밍, 외부 톤에서 빼야 할 내부 표현, 조건부 문구 |

- 짧은 글은 **Quick Strike**(인라인 비평), 장문·공식 보고서는 **Deep Audit**(감수 리포트)로 받는다.
- 호출 예: 초안을 제시하며 "이거 발주처 보내기 전에 레드팀 해줘" → jc-redteam이 외부 감사관 시각으로 점검.
- 데이터 봉투가 필요한 체이닝은 `jc-design-system/references/chaining-protocol.md`의 `ChainPayload/v1` 규약을 따른다(대개 본 스킬은 텍스트 직접 전달로 충분).

## 7. RULE-NO-COMPANY — 회사·개인 식별정보 하드코딩 금지

본 스킬 군은 특정 소속사가 아닌 **개인(MICE 전략가) 자산**이다. 회사명·개인 실명·발주처·부서명은 **절대 하드코딩하지 않고**, 매 산출 시 사용자가 제공하는 **외부 주입 변수**로만 처리한다.

**표준 변수 슬롯** (가이드·예시 전반에서 사용):

| 변수 | 의미 |
|------|------|
| `{{client_company}}` | 발주처·고객사 |
| `{{author_name}}` | 작성자(발신자) 실명 |
| `{{author_title}}` | 작성자 직함 |
| `{{company_name}}` | 작성자 소속(자사) |
| `{{personal_brand}}` | 개인 브랜드(Track B) |
| `{{event_name}}` / `{{partner_company}}` / `{{venue}}` 등 | 행사·협력사·장소 등 도메인 슬롯 |

- 가이드 안의 모든 MICE 예시는 **가상**이며, 행사·발주처·인명은 위 placeholder로만 표기한다.
- 일반화 표현은 허용: "본 행사 사무국", "발주처", "협력사", "참가자", "본 PCO".
- **체크**: 산출물·가이드에 구체 상호·실명·부서명이 0건인지 확인. 정본: `jc-design-system/references/shared-rules.md#RULE-NO-COMPANY`.
