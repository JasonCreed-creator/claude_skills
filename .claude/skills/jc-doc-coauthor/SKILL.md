# jc-doc-coauthor

MICE 산문형 문서를 사용자와 **함께 써 나가는** 3단계 공동 작성 워크플로우다. Claude가 받아쓰는 게 아니라 **능동적 가이드**로서 사용자의 머릿속 맥락을 끌어내고, 섹션별로 옵션을 펼쳐 고르게 하고, 마지막엔 적대적 검증으로 맹점을 친다.

원본 프리셋(`doc-coauthoring`)의 3단계 골격을 유지하되 두 가지를 바꿨다:
1. **③ Reader Testing을 `jc-redteam` 적대 검증으로 대체** — 원본은 "맥락 없는 fresh Claude"에게 문서를 던져 가독성을 봤다. jc 생태계엔 이미 18년 경력 외부 감사관 시각의 레드팀이 있으므로, 그 자리에 jc-redteam을 끼운다. 맹점·모순·가독성을 *우호적 독해*가 아니라 *적대적 공격*으로 검증한다(§4).
2. **MICE 문서 6종에 특화** — 행사 기획서·운영계획서·전략 메모·의사결정 문서·사후 결과보고 개요·RFC. 유형별 섹션 골격은 `references/mice-doc-types.md`.

## 1. 본 스킬이 다루는 것 / 다루지 않는 것

### 다루는 것 (DO)
- 산문형(Markdown/문서) MICE 문서를 **0 → 1로 함께 작성**하는 단계적 프로세스
- 사용자 머릿속 맥락을 구조화된 질문으로 끌어내기(컨텍스트 수집)
- 섹션별 브레인스토밍(5~20개 옵션) → 큐레이션 → 초안 → 외과적 편집
- 완성 직전 `jc-redteam` 적대 검증(짧은 결론=Quick Strike, 장문 문서=Deep Audit)
- 시각 아티팩트가 필요하면(다이어그램·표지) jc-design-system 토큰 적용

### 다루지 않는 것 (DON'T)
- 발주처용 **제안서 슬라이드(PPTX)** 생성 → `mice-proposal`
- 회의 transcript/메모의 8축 정리 → `mice-meeting-minutes`
- 이미 완성된 결론·문서의 **검증만** 단독 요청 → `jc-redteam` 직접
- 디자인 토큰 정의·테마/오버레이 적용 → `jc-design-system` / `jc-theme-factory`
- RFP·공고 분석 → `mice-rfp-analyzer` · 견적서 → `mice-estimate` · 발표 대본 → `pt-script`

> **mice-proposal와의 경계**: proposal은 *발주처에게 보여줄 완성 슬라이드 데크*를 만든다. 본 스킬은 *사고를 정리하며 산문 문서를 함께 써 나가는 과정*이다. 산출물 형태(슬라이드 vs 산문)와 행위(생성 vs 공동 집필)가 다르다. 단, 본 스킬로 정리한 기획 산문은 mice-proposal의 좋은 입력이 된다(§7).

## 3. 왜 3단계인가 — 설계 의도

이 워크플로우의 가치는 **순서**에 있다. 좋은 MICE 문서가 무너지는 지점은 대부분 "맥락이 작성자 머릿속에만 있어서"다. 그래서 쓰기 전에 그걸 비우고(①), 한 번에 다 쓰려 하지 않고 섹션별로 골라 쌓고(②), 다 쓴 뒤 *내가 아닌 사람* 눈으로 친다(③).

```
① 컨텍스트 수집     작성자 머릿속 ≈ Claude 머릿속 으로 격차 줄이기
        ↓           (이게 안 되면 이후 모든 가이드가 헛다리)
② 구조·정제        섹션별 브레인스토밍 → 큐레이션 → 초안 → 외과적 편집
        ↓           (한 번에 완성하려 들지 않는다. 고르고 버리며 쌓는다)
③ 리더 테스트       jc-redteam 적대 검증 — 맹점·모순·가독성을 공격
        ↓           (작성자에겐 당연한 것이 독자에겐 구멍이다)
[사용자 최종 책임 read-through]
```

각 단계는 사용자가 원하면 건너뛸 수 있다. **억압적으로 강제하지 않는다** — 프로세스는 사용자의 사고를 돕는 도구이지 관문이 아니다. 다만 건너뛰면 무엇을 잃는지 1줄로 알린다.

### 톤 원칙 (전 단계 공통)
- **한국어 우선**, 푸시형. "~합니다" 통보형으로 다음 행동을 짧게 제시한다.
- 프로세스를 *팔지 않는다*. 설명은 사용자 행동에 영향을 줄 때만 1줄.
- 사용자가 직접 문서를 고치면 그 변경을 다음 섹션 스타일 학습에 반영한다.
- 편집은 항상 **외과적**(해당 부분만 교체). 전체 문서를 다시 출력하지 않는다.

## 4. 초기 제안 (워크플로우 진입)

긴 글쓰기 신호가 감지되면, 3단계 공동 작성을 **제안**한다. 세 단계를 한 문장씩 설명하고 — "이렇게 하면 나중에 다른 사람이 읽을 때(특히 그 사람이 Claude에 붙여넣을 때)도 잘 작동하는 문서가 됩니다" — 이 방식으로 갈지, 자유롭게 쓸지 묻는다.

- 사용자가 거절 → 자유 모드로 작성.
- 수락 → **Stage 1**로.
- 어떤 MICE 문서 유형인지 이미 명확하면 `references/mice-doc-types.md`에서 해당 골격을 미리 참조한다.

## Stage 1 — 컨텍스트 수집

**목표**: 작성자가 아는 것과 Claude가 아는 것의 격차를 좁힌다. 이게 돼야 이후 가이드가 똑똑해진다.

### 5W1H 메타 질문 (시작)
문서의 *메타 컨텍스트*부터 묻는다. 약식으로 답하거나 자유롭게 쏟아내도 된다고 알린다.

1. 어떤 문서인가? (기획서/운영계획서/전략 메모/의사결정 문서/결과보고 개요/RFC)
2. 1차 독자는 누구인가? (발주처 의사결정자 / 내부 경영진 / 협력사 / 팀)
3. 읽고 난 뒤 **어떤 행동·판단**이 일어나길 원하는가? (승인/예산 배정/방향 합의…)
4. 따라야 할 템플릿·양식이 있는가? (있으면 파일/링크 공유 요청)
5. 그 외 제약·맥락은? (마감, 정치적 민감성, 과거 이력)

문서 유형·독자가 정해지면 `references/stage-questions.md`의 **유형별 핵심 질문 세트**로 좁혀 묻는다.

### 정보 덤프
메타 질문 후, **갖고 있는 맥락을 전부 쏟아내달라**고 청한다. 정리하지 말고 그냥 다 꺼내라고 안내한다. 청할 정보 예시:
- 프로젝트/문제 배경, 왜 지금 이 문서가 필요한가
- 관련 회의·합의·기존 문서 (있으면 `mice-meeting-minutes` 산출 회의록을 입력으로 받을 수 있음 — §7)
- 검토했으나 택하지 않은 대안과 그 이유
- 조직 맥락(이해관계자 역학, 과거 사건, 발주처 성향)
- 일정 압박·예산 제약·운영 의존성

> **연동(Integrations) 활용**: Slack·Google Drive 등 커넥터가 붙어 있으면 팀 채널·공유 문서에서 맥락을 직접 끌어올 수 있음을 알린다. 없으면 관련 내용을 붙여넣어 달라고 청한다(설정에서 커넥터 활성화 안내).

> **기존 공유 문서 편집 시 — 이미지 alt-text 점검**: 편집 대상이 이미 있는 공유 문서면 현재 상태를 읽어 **alt-text 없는 이미지**가 있는지 확인한다. 있으면 "무맥락 독자(문서를 붙여넣어 읽는 다른 Claude 포함)는 이 이미지를 못 읽는다"고 알리고 alt-text 생성을 제안한다 — 수락 시 각 이미지를 채팅에 붙여넣어 설명형 alt-text를 만든다.

### 명료화 질문
사용자가 초기 덤프를 마쳤다는 신호를 주면, **갭 기반 5~10개 번호 질문**을 생성한다. "1: 응, 2: #채널 참고, 3: 아니오(하위호환)" 식 약식 답변·링크·채널 지정 모두 허용한다고 알린다.

**종료 조건**: 질문이 *이해를 보여줄 때* — 엣지케이스·트레이드오프를 기본 설명 없이 물을 수 있게 되면 충분하다. 더 줄 맥락이 있는지 묻고, 없으면 **Stage 2**로.

## Stage 2 — 구조·정제

**목표**: 문서를 **섹션 단위로** 브레인스토밍·큐레이션·반복 정제하며 쌓는다. 한 번에 완성하려 들지 않는다.

### 섹션 구조 합의
- 구조가 명확하면 어느 섹션부터 시작할지 묻는다. **미지의 것이 가장 많은 섹션부터** 권한다(의사결정 문서=핵심 제안, RFC=설계안, 기획서=콘셉트). 요약·개요는 **맨 마지막**.
- 구조를 모르면 문서 유형에 맞는 **3~5개 섹션을 제안**한다 → `references/mice-doc-types.md`의 유형별 골격 사용.
- 합의되면 **모든 섹션 헤더 + `[작성 예정]` 플레이스홀더**로 초기 스캐폴드를 만든다.
  - 아티팩트 접근 가능(claude.ai) → `create_file`로 아티팩트 스캐폴드.
  - 아티팩트 불가(파일 환경) → 작업 디렉터리에 적절한 이름의 `.md` 파일(`decision-doc.md`, `event-plan.md` 등).

### 섹션별 6스텝 (각 섹션 반복)
원본의 장문 절차를 6스텝으로 압축한다:

1. **명료화 질문** — 해당 섹션에 무엇을 담을지 5~10개 질문. 약식 답변 허용.
2. **브레인스토밍** — 섹션 복잡도에 따라 **5~20개 옵션**을 번호로 펼친다. 사용자가 잊었을 맥락·아직 안 나온 각도를 적극 발굴한다. (브레인스토밍 목록은 *대화*로만 — 아티팩트에 쓰지 않는다.)
3. **큐레이션** — 무엇을 남길/뺄/합칠지 묻는다("1,4,7 유지 / 3 삭제(1과 중복) / 11,12 통합"). 간단한 이유도 청해 다음 섹션 우선순위를 학습한다. 자유 피드백("대충 좋아")이면 의도를 파싱해 반영한다.
4. **갭 체크** — 고른 것 기준으로 빠진 게 없는지 1회 확인.
5. **초안** — `str_replace`로 해당 섹션 플레이스홀더만 실제 내용으로 교체. 다 쓰면 읽어보고 *직접 고치지 말고 무엇을 바꿀지 말해달라*고 청한다(스타일 학습용. 첫 섹션에서 1회 안내).
6. **반복 정제** — 피드백마다 `str_replace`로 외과적 편집. 전체 재출력 금지.

> **아티팩트 링크 제공**: 아티팩트 지원 서피스(claude.ai)에서는 초안(Step 5)·편집(Step 6)을 할 때마다 **매번 아티팩트 링크를 제공**한다. 파일 환경에서는 편집 완료만 확인한다.

> **품질 체크**: 한 섹션에서 실질 변경 없는 반복이 3회 연속되면 "정보 손실 없이 덜어낼 부분 없는지" 묻고 다음 섹션으로.

### 완성 근처 (섹션 80%+)
전체 문서를 다시 읽고 점검한다:
- 섹션 간 흐름·일관성, 중복·모순
- "slop"(일반적 채움말), 모든 문장이 제 몫을 하는가

전 섹션이 끝나면 전체를 한 번 더 통독·코멘트한 뒤, **Stage 3(리더 테스트)로 갈지** 묻는다.

### 시각 아티팩트가 필요하면 (선택)
문서에 다이어그램(워크플로우·조직도·타임라인)·표지·핵심 도식이 필요하면 jc-design-system을 적용한다. **이 스킬의 본령은 산문**이므로, 시각물은 보조로만.

- **토큰 값을 본문/코드에 하드코딩하지 않는다.** SoT 런타임 참조: `jc-design-system/references/signature-tokens.md §6 JSON`(색·타이포·사이즈·간격). 다크/인쇄는 `mode-mapping.md`.
- 핵심 값(참조용): primary `#0A2540`(Deep Navy)·accent `#2962FF`(Electric Blue)·폰트 Pretendard(한)/Inter(영)/JetBrains Mono(숫자) — **값은 위 SoT가 정본**, 여기 적은 건 식별용.
- 복합 인터랙티브 도식이 필요하면 `jc-artifact-builder`, 테마/오버레이 적용은 `jc-theme-factory`로 위임.
- 공통 룰: `RULE-WCAG`(본문 4.5:1↑)·`RULE-PRINT-LIGHT`(인쇄 라이트 강제). 정본 `jc-design-system/references/shared-rules.md`.

## Stage 3 — 리더 테스트 = jc-redteam 적대 검증 ⭐

**이 개조의 핵심 차별점.** 원본은 "맥락 없는 fresh Claude"에게 문서를 던져 독자 입장을 흉내 냈다. 본 스킬은 그 자리에 **`jc-redteam`**(18년 경력 외부 감사관 시각의 적대적 레드팀)을 끼운다. *우호적 독해*가 아니라 *적대적 공격*으로 맹점·모순·가독성·논리 비약을 친다. 재발명 금지 — 검증은 생태계의 전용 게이트에 위임한다(플레이북 §6).

> **왜 fresh Claude 대신 jc-redteam인가**: fresh Claude는 "이해되나?"를 본다. jc-redteam은 "이 결론이 틀렸다면 어디서 틀렸나?"를 본다. MICE 문서(의사결정·기획)는 *읽혀서가 아니라 실행돼서* 비용을 치르므로, 통과 기준은 가독성이 아니라 **실행해도 안전한가**여야 한다.

### 모드 선택 (jc-redteam에 위임되는 분기)
jc-redteam은 입력 길이·형태로 모드를 자동 판정한다(jc-redteam SKILL §4). 본 스킬은 문서 성격에 맞춰 다음을 넘긴다:

| 문서 성격 | jc-redteam 모드 | 산출 |
|----------|----------------|------|
| 짧은 결론형(1~2p 전략 메모·의사결정 한 줄 결론·요약) | **Quick Strike** | 인라인 비평 (결론 정의→핵심 결함→Steelman→종합 판정) |
| 장문 문서(기획서·운영계획서·RFC·결과보고 개요) | **Deep Audit** | 구조화 감수 리포트(.md, 요청 시 .docx) |

모호하면 사용자에게 1회 확인. 두 모드 모두 **3축(내용 검증·오탈자 감수·대안 제시)**으로 분석하고 결함마다 **심각도(🔴Critical/🟡Major/🟢Minor)**를 부여한다(jc-redteam SKILL §5·§6).

### 호출 절차
1. **검증 대상 전달**: 완성 문서(또는 직전 결론)를 jc-redteam에 넘긴다. 문서 유형을 함께 알려 jc-redteam의 *유형별 집중 공격 포인트*가 걸리게 한다 — 매핑은 `jc-redteam/references/chaining-guide.md`. (예: 의사결정 문서 ≈ "GO/NO-GO 판정"의 숨은 가정·낙관편향 공격 포인트를 차용, RFC/기획서는 "논리 비약·누락 관점·내부 모순" 중심.)
2. **3축 결과 수령**: Critical→Major→Minor 순으로 결함과 종합 판정(✅결론 유지 / ⚠️조건부 보완 / 🔴결론 재검토)을 받는다.
3. **리팩터 루프**: 발견된 결함이 걸린 섹션으로 **Stage 2 정제 루프로 되돌아간다.** Critical·Major부터 고친다.
4. **재검증**: 수정 후 jc-redteam을 다시 돌려 *결론 유지* 판정이 나올 때까지 반복.

> jc-redteam은 산출물을 **재생성하지 않는다.** 결함을 찾아 지적·교정·대안 제시까지만 한다. 실제 수정(섹션 재작성)은 본 스킬이 Stage 2 루프로 수행한다.

### 종료 조건
jc-redteam이 새 Critical/Major를 더 못 찾고 **✅결론 유지** 판정을 줄 때 문서가 준비된 것이다.

## 최종 점검 (사용자 책임)

리더 테스트 통과 후, 완료 선언 전에 알린다:
1. **본인이 직접 통독**하라 — 이 문서의 소유자이자 품질 책임자는 사용자다.
2. 사실·링크·수치·고유명사를 다시 확인하라.
3. 의도한 임팩트(승인/합의/방향)를 실제로 달성하는지 검증하라.

마지막 팁:
- 이 대화를 부록에 링크하면 독자가 문서가 어떻게 만들어졌는지 볼 수 있다.
- 부록으로 본문을 비대화하지 않고 깊이를 더한다.
- 실제 독자 피드백이 오면 문서를 갱신한다.

## 5. RULE-NO-COMPANY (회사·실명 외부 주입)

문서 본문에 **특정 회사명·개인 실명·부서명을 하드코딩하지 않는다.** 발주처·발행자·작성자·조직은 모두 **외부 주입 변수**로 처리하고 사용자가 매 작성 시 제공한다.
- 허용: "발주처", "본 사무국", "본 PCO", `T社`, "발표 주체" 등 일반화 표현 + 변수 슬롯 `{{client_company}}`·`{{author_name}}`·`{{personal_brand}}`·`{{author_title}}`·`{{company_name}}`.
- 정본: `jc-design-system/references/shared-rules.md#RULE-NO-COMPANY`.
- jc-redteam 검증 시에도 "회사 종속 표현 0건"을 점검 항목에 포함한다.

## 6. 표준 워크플로우 (요약)

```
[긴 글쓰기 신호] → 3단계 제안 (거절 시 자유 모드)
        ↓
Stage 1 컨텍스트 수집  ── 5W1H 메타 → 정보 덤프 → 명료화 질문(갭 기반)
        ↓               (종료: 엣지케이스를 기본 설명 없이 물을 수 있을 때)
Stage 2 구조·정제      ── 섹션 합의 → 스캐폴드 → [섹션별 6스텝]×N → 전체 통독
        ↓               (필요 시 시각 아티팩트 jc-design-system 적용)
Stage 3 리더 테스트    ── jc-redteam 호출 (짧음=Quick Strike / 장문=Deep Audit)
        ↓               3축 검증 → 심각도 → 종합 판정 → [결함 섹션 Stage 2로 루프]
[✅ 결론 유지] → 사용자 최종 통독 → 완료
```

## 7. 생태계 연결

- **검증(핵심)**: `jc-redteam` — Stage 3 전체. 짧은 결론=Quick Strike, 장문=Deep Audit. 유형별 공격 포인트는 `jc-redteam/references/chaining-guide.md`.
- **입력 체이닝**: `mice-meeting-minutes` Discovery/협의 회의록을 Stage 1 컨텍스트로 받을 수 있다(니즈·예산·일정·결정사항). 봉투는 `ChainPayload/v1`(`jc-design-system/references/chaining-protocol.md`).
- **출력 체이닝**: 본 스킬로 정리한 기획 산문 → `mice-proposal`(제안서 슬라이드)·`mice-estimate`(견적) 입력으로 전달 가능.
- **디자인**: 시각 아티팩트는 `jc-design-system` SoT 런타임 참조. 복합 인터랙티브는 `jc-artifact-builder`, 테마는 `jc-theme-factory`.

## 9. 운영 원칙 / 한계

- **사용자 agency 우선**: 단계 건너뛰기·자유 모드 전환을 항상 허용한다. 프로세스는 사고를 돕는 도구이지 관문이 아니다.
- **외과적 편집 고정**: 모든 수정은 `str_replace`로 해당 부분만. 전체 문서 재출력은 컨텍스트 낭비이자 사용자 혼란.
- **브레인스토밍은 대화로**: 옵션 목록을 아티팩트/파일에 쓰지 않는다. 확정된 본문만 문서에 들어간다.
- **검증은 위임**: 가독성·논리 검증을 자체 흉내 내지 말고 `jc-redteam`에 넘긴다(재발명 금지).
- **본령은 산문**: 시각물·슬라이드·대시보드가 주가 되면 잘못 트리거된 것 — mice-proposal/mice-dashboard/jc-artifact-builder로 보낸다.
