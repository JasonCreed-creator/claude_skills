# jc-doc-coauthor

MICE 산문형 문서를 사용자와 **함께 써 나가는** 3단계 공동 작성 워크플로우다. Claude가 받아쓰는 게 아니라 **능동적 가이드**로서 사용자의 머릿속 맥락을 끌어내고, 섹션별로 옵션을 펼쳐 추천안으로 쌓고, 마지막엔 적대적 검증으로 맹점을 친다.

원본 프리셋(`doc-coauthoring`)의 3단계 골격을 유지하되 세 가지를 바꿨다:
1. **③ Reader Testing → 레드팀 검증(`jc-redteam`)** — 원본은 "맥락 없는 fresh Claude"에게 문서를 던져 가독성을 봤다. 본 스킬은 그 자리에 jc-redteam(외부 감사관 시각의 적대적 레드팀)을 끼운다. 맹점·모순·가독성을 *우호적 독해*가 아니라 *적대적 공격*으로 검증한다.
2. **기본값 진행** — 단계·섹션마다 "다음으로 갈까요?"를 묻지 않는다. 합리적 기본값으로 진행하고 고른 기본값을 한 줄로 밝힌다. 사용자 확인은 **기획안(구조·핵심 메시지) 1회**뿐이다.
3. **MICE 문서 6종 특화** — 행사 기획서·운영계획서(공동 집필 시만, 골격 정본은 `mice-ops-docs`)·전략 메모·의사결정 문서·RFC·메시지 기획 문서(행사명·슬로건). 유형별 섹션 골격은 `references/mice-doc-types.md`, 메시지 기획 절차는 `references/message-planning.md`.

## 1. 다루는 것 / 다루지 않는 것

### 다루는 것 (DO)
- 산문형 MICE 문서를 **0 → 1로 함께 작성**하는 단계적 프로세스
- 사용자 머릿속 맥락을 구조화된 질문으로 끌어내기(컨텍스트 수집)
- 섹션별 브레인스토밍(5~20개 옵션) → 추천안 큐레이션 → 초안 → 외과적 편집
- 완성 직전 `jc-redteam` 레드팀 검증(짧은 결론=Quick Strike, 장문=Deep Audit)
- 행사명·슬로건·태그라인·핵심 메시지 후보를 펼쳐 ★추천 + 근거 + 버린 안으로 확정하는 **메시지 기획 문서**(`references/message-planning.md`)
- 문서에 들어갈 도식·표지가 필요하면 `jc-design-system` 토큰 적용

### 다루지 않는 것 (DON'T)
- 발주처용 **제안서·소개서 슬라이드(PPTX)** → `jc-pptx`
- 회의 transcript/메모 정리 → `mice-meeting-minutes`
- 이미 완성된 결론·문서의 **검증만** 단독 요청 → `jc-redteam` 직접
- 운영계획서·팀 지침·그라운드룰·KPI 대시보드 **완성본**("바로 내줘") → `mice-ops-docs`. 본 스킬은 "같이 쓰자"·"섹션별로 묻고 가자" 신호가 있을 때만, 그쪽 골격(`mice-ops-docs/references/ops-plan.md`)으로 함께 쓴다
- 결과보고서("같이 써 나가자" 포함, 작성 방식 불문) → `mice-aftermath`
- 디자인 토큰 값 정의·수정 → `jc-design-system` (토큰 값·룰 조회도 그쪽, 적용은 본 스킬이 런타임 참조)
- KV 제작 가이드 → `jc-kv-guide`(메시지 기획 문서가 그 입력) · 경쟁 포지셔닝 분석 → `jc-strategy-canvas`
- RFP·공고 분석 → `mice-rfp-analyzer` · 견적서 → `mice-estimate` · 발표 대본 → `pt-script`

> **jc-pptx와의 경계**: jc-pptx는 *발주처에게 보여줄 완성 슬라이드 덱*을 만든다. 본 스킬은 *사고를 정리하며 산문 문서를 함께 써 나가는 과정*이다. 단, 본 스킬로 정리한 기획 산문은 jc-pptx의 좋은 입력이 된다(§7).

| 사용자 입력 | 본 스킬 | 사용 스킬 |
|------------|:------:|----------|
| "이 행사 기획서 같이 써줘" | ✅ | jc-doc-coauthor |
| "의사결정 문서 초안 잡아줘" | ✅ | jc-doc-coauthor |
| "이 결정에 대한 RFC 써줘" | ✅ | jc-doc-coauthor |
| "발주처 제안서 PPTX 만들어줘" | ❌ | jc-pptx |
| "이 회의록 정리해줘" + transcript | ❌ | mice-meeting-minutes |
| "이 다 쓴 문서 허점 때려줘" | ❌ | jc-redteam |

## 2. 왜 3단계인가

좋은 MICE 문서가 무너지는 지점은 대부분 "맥락이 작성자 머릿속에만 있어서"다. 그래서 쓰기 전에 그걸 비우고(①), 한 번에 다 쓰려 하지 않고 섹션별로 골라 쌓고(②), 다 쓴 뒤 *내가 아닌 사람* 눈으로 친다(③).

```
① 컨텍스트 수집     작성자 머릿속 ≈ Claude 머릿속 으로 격차 줄이기
        ↓
② 구조·정제        기획안 1회 확인 → 섹션별 브레인스토밍 → 추천안 → 초안 → 외과적 편집
        ↓
③ 레드팀 검증       jc-redteam 적대 검증 — 맹점·모순·가독성을 공격
        ↓
[사용자 최종 책임 read-through]
```

단계 사이에서 멈춰 묻지 않는다. 사용자가 "자유롭게 써줘"·"검증은 빼"라고 하면 그대로 따르고, 건너뛰면 무엇을 잃는지 1줄로만 알린다.

### 톤 원칙 (전 단계 공통)
- **한국어 우선**. "~합니다" 통보형으로 다음 행동을 짧게 제시한다.
- 프로세스를 *팔지 않는다*. 설명은 사용자 행동에 영향을 줄 때만 1줄.
- 사용자가 직접 문서를 고치면 그 변경을 다음 섹션 스타일 학습에 반영한다.
- 편집은 항상 **외과적**(해당 부분만 교체). 전체 문서를 다시 출력하지 않는다.

## 3. 산출 형식 (기본값)

| 상황 | 산출 |
|------|------|
| Claude Docs 커넥터 사용 가능 (기본) | **Claude Docs 문서** — 스캐폴드(제목·섹션 헤더·`[작성 예정]`)를 먼저 만들고 섹션을 채운다. docs 스킬 지침을 먼저 따른다 |
| 커넥터 없음(로컬 파일 환경) | 작업 폴더에 `.md` 파일(`decision-doc.md`, `event-plan.md` 등) |
| 사용자가 Word·.docx를 명시 | docx 스킬로 변환(Claude Docs에서 내보내기 가능하면 그것으로) |

고른 형식은 시작할 때 한 줄로 밝힌다. 문서 공유·외부 발송은 사용자가 정한다(되돌릴 수 없는 작업).

## Stage 1 — 컨텍스트 수집

**목표**: 작성자가 아는 것과 Claude가 아는 것의 격차를 좁힌다.

### 메타 컨텍스트 (5W1H)
이미 받은 자료로 답할 수 있으면 묻지 않고 채운 뒤 '가정'으로 표기한다. 빈칸만 한 번에 묶어 묻는다.
1. 어떤 문서인가? (기획서/운영계획서/전략 메모/의사결정 문서/RFC/메시지 기획) — 결과보고면 `mice-aftermath`로 넘긴다
2. 1차 독자는? (발주처 의사결정자 / 내부 경영진 / 협력사 / 팀)
3. 읽고 난 뒤 **어떤 행동·판단**이 일어나길 원하는가?
4. 따라야 할 템플릿·양식이 있는가?
5. 그 외 제약·맥락은? (마감, 정치적 민감성, 과거 이력)

유형·독자가 정해지면 `references/stage-questions.md`의 **유형별 핵심 질문 세트**로 좁힌다.

### 정보 덤프
갖고 있는 맥락을 정리하지 말고 다 꺼내 달라고 청한다 — 배경, 관련 회의·합의(`mice-meeting-minutes` 회의록 입력 가능), 버린 대안과 이유, 이해관계자 역학, 일정·예산 제약.

> **연동 활용**: Slack·Google Drive 등 커넥터가 붙어 있으면 팀 채널·공유 문서에서 맥락을 직접 끌어온다. 없으면 붙여넣어 달라고 청한다.

> **기존 공유 문서 편집 시 — 이미지 alt-text 점검**: 편집 대상 문서에 alt-text 없는 이미지가 있으면 "무맥락 독자(문서를 붙여넣어 읽는 다른 Claude 포함)는 이 이미지를 못 읽는다"고 알리고 설명형 alt-text를 만들어 넣는다.

### 명료화 질문
덤프가 끝나면 **갭 기반 5~10개 번호 질문**을 한 번에 낸다. 약식 답변·링크·채널 지정 모두 허용. 질문이 엣지케이스·트레이드오프를 기본 설명 없이 물을 수 있을 만큼 이해가 차면 바로 Stage 2로 넘어간다(넘어갈지 묻지 않는다).

## Stage 2 — 구조·정제

**목표**: 문서를 **섹션 단위로** 쌓는다. 한 번에 완성하려 들지 않는다.

### 기획안 — 1회 확인
- 문서 유형에 맞는 **섹션 구조**(`references/mice-doc-types.md` 골격)와 **핵심 메시지 1문장**을 제시하고 한 번만 확인받는다. 사용자가 구조를 이미 줬거나 "바로 써"라고 했으면 확인 없이 진행한다.
- 확정되면 §3 형식으로 **스캐폴드**(모든 섹션 헤더 + `[작성 예정]`)를 만든다.
- 작성 순서 기본값: **미지의 것이 가장 많은 섹션부터**(의사결정 문서=핵심 제안, RFC=설계안, 기획서=콘셉트, 메시지 기획=포지셔닝 한 문장), 요약·개요는 맨 마지막.

### 섹션별 5스텝 (각 섹션 반복, 기본값 진행)
1. **명료화** — 섹션에 담을 것 중 자료로 답이 안 되는 빈칸만 묻는다(없으면 생략).
2. **브레인스토밍** — 섹션 복잡도에 따라 **5~20개 옵션**을 번호로 펼치고, 그중 **추천 조합에 ★**을 붙인다. 목록은 대화로만 — 문서에 쓰지 않는다.
3. **초안** — 추천 조합으로 바로 해당 섹션 플레이스홀더만 교체한다. "★ 1·4·7로 썼습니다 — 바꿀 번호만 말해 주세요" 한 줄로 알린다. 첫 섹션에서 1회, *직접 고치기보다 무엇을 바꿀지 말해 달라*고 안내한다(스타일 학습용).
4. **반복 정제** — 피드백이 오면 외과적 편집. 전체 재출력 금지. 피드백이 없으면 다음 섹션으로 진행한다.
5. **갭 체크** — 섹션을 마칠 때 빠진 관점이 있으면 1줄로 짚고 넣는다.

> Claude Docs·아티팩트 서피스에서는 초안·편집마다 문서 링크를 준다. 파일 환경에서는 편집 완료만 알린다.

> **품질 체크**: 한 섹션에서 실질 변경 없는 반복이 3회 연속되면 덜어낼 부분을 제안하고 다음 섹션으로.

### 완성 근처 (섹션 80%+)
전체를 다시 읽고 섹션 간 흐름·중복·모순, "slop"(일반적 채움말)을 점검·수정한 뒤 **바로 Stage 3(레드팀 검증)으로 간다**.

### 도식·표지가 필요하면 (선택)
본령은 산문이므로 시각물은 보조로만.
- 기본 룩은 **리멤버 웜 페이퍼**(`jc-design-system` v2). 토큰 값은 하드코딩하지 않고 `jc-design-system/references/signature-tokens.md §6 JSON`에서 런타임 참조(다크·인쇄는 `mode-mapping.md`). 구 네이비 시그니처는 `legacy-jc` 오버레이로, 명시 요청 시만.
- 서체 Pretendard. 오렌지 강조는 큰 글자 전용, 작은 글자 강조는 accent-deep.
- 이미지 생성이 필요하면 Higgsfield(RULE-VISUAL-ROUTING).
- 공통 룰: `RULE-WCAG`(본문 4.5:1↑)·`RULE-PRINT-LIGHT`. 정본 `jc-design-system/references/shared-rules.md`.

## Stage 3 — 레드팀 검증 = jc-redteam 적대 검증

**fresh Claude 대신 jc-redteam인 이유**: fresh Claude는 "이해되나?"를 본다. jc-redteam은 "이 결론이 틀렸다면 어디서 틀렸나?"를 본다. MICE 문서는 *읽혀서가 아니라 실행돼서* 비용을 치르므로 통과 기준은 **실행해도 안전한가**다. 검증은 자체 흉내 내지 않고 위임한다.

### 모드 선택 (jc-redteam에 위임되는 분기)
jc-redteam은 입력 길이·형태로 모드를 자동 판정한다(jc-redteam SKILL §4). 본 스킬은 문서 성격에 맞춰 다음을 넘긴다:

| 문서 성격 | jc-redteam 모드 | 산출 |
|----------|----------------|------|
| 짧은 결론형(1~2p 전략 메모·의사결정 한 줄 결론·요약·메시지 기획 ★추천안) | **Quick Strike** | 인라인 비평 (결론 정의→핵심 결함→Steelman→종합 판정) |
| 장문 문서(기획서·운영계획서·RFC) | **Deep Audit** | 구조화 감수 리포트(.md, 요청 시 .docx) |

모호하면 장문 기준(Deep Audit)으로 진행하고 그 선택을 한 줄로 밝힌다. 두 모드 모두 **3축(내용 검증·오탈자 감수·대안 제시)**으로 분석하고 결함마다 **심각도(🔴Critical/🟡Major/🟢Minor)**를 부여한다(jc-redteam SKILL §5·§6).

### 호출 절차
1. **검증 대상 전달**: 완성 문서(또는 직전 결론)를 jc-redteam에 넘긴다. 문서 유형을 함께 알려 jc-redteam의 *유형별 집중 공격 포인트*가 걸리게 한다 — 정본은 `jc-redteam/references/chaining-guide.md` §jc-doc-coauthor(본 스킬은 공격 포인트를 따로 적지 않는다).
2. **3축 결과 수령**: Critical→Major→Minor 순으로 결함과 종합 판정(✅결론 유지 / ⚠️조건부 보완 / 🔴결론 재검토)을 받는다.
3. **리팩터 루프**: 발견된 결함이 걸린 섹션으로 **Stage 2 정제 루프로 되돌아간다.** Critical·Major부터 고친다.
4. **재검증**: 수정 후 jc-redteam을 다시 돌려 *결론 유지* 판정이 나올 때까지 반복.

> jc-redteam은 산출물을 **재생성하지 않는다.** 결함을 찾아 지적·교정·대안 제시까지만 한다. 실제 수정(섹션 재작성)은 본 스킬이 Stage 2 루프로 수행한다.

### 종료 조건
jc-redteam이 새 Critical/Major를 더 못 찾고 **✅결론 유지** 판정을 줄 때 문서가 준비된 것이다.

## 최종 점검 (사용자 책임)

레드팀 검증 통과 후, 완료 선언과 함께 알린다:

2. 사실·링크·수치·고유명사를 다시 확인하라.
3. 의도한 임팩트(승인/합의/방향)를 실제로 달성하는지 검증하라.

## 7. 생태계 연결

- **검증**: `jc-redteam` — Stage 3 전체. 유형별 공격 포인트 정본은 `jc-redteam/references/chaining-guide.md` §jc-doc-coauthor.
- **세션·서브에이전트**: 장문 문서를 나눠 쓰거나 병렬 조사가 필요하면 `jc-session-protocol`.
- **입력 체이닝**: `mice-meeting-minutes` 회의록·`mice-rfp-analyzer` 분석을 Stage 1 컨텍스트로 받는다. 봉투는 `ChainPayload/v1`(`jc-design-system/references/chaining-protocol.md`).
- **출력 체이닝**: 기획 산문 → `jc-pptx`(제안서·소개서 슬라이드)·`mice-estimate`(견적) 입력. 메시지 기획 문서 → `jc-kv-guide`(`source: jc-doc-coauthor` — `doc_meta`·`key_message`·`sections`, 예시 `references/message-planning.md` §5). 본 source는 `jc-design-system` chaining-protocol §3 enum에 '메시지 기획 문서 봉투만 산출(선택)'로 등록돼 있다(v2.2.0).
- **이웃 산출 스킬**: 운영계획서 골격 정본 `mice-ops-docs/references/ops-plan.md` §2 · 결과보고 `mice-aftermath`.
- **디자인**: 토큰 값·룰 조회는 `jc-design-system`(적용은 본 스킬이 런타임 참조).

## 9. 운영 원칙 / 한계

- **기본값 진행**: 되돌릴 수 있는 작업(초안·섹션·파일)은 묻지 않고 진행하고 고른 기본값을 한 줄로 밝힌다. 사용자는 언제든 번호·한 줄로 뒤집을 수 있다.
- **외과적 편집 고정**: 수정은 해당 부분만. 전체 재출력 금지.
- **브레인스토밍은 대화로**: 옵션 목록을 문서에 쓰지 않는다. 확정 본문만 문서에 들어간다.
- **검증은 위임**: 가독성·논리 검증은 `jc-redteam`에 넘긴다.
- **본령은 산문**: 슬라이드가 주가 되면 `jc-pptx`, 결과보고는 작성 방식 불문 `mice-aftermath`, 운영계획서·팀 지침·그라운드룰·KPI 대시보드 완성본은 `mice-ops-docs`로 보낸다(운영계획서는 "같이 쓰자"·"섹션별로 묻고 가자" 신호가 있을 때만 본 스킬).
