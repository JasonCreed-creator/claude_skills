# jc-orchestrator

복합 작업을 **멀티 에이전트 팀으로 설계**하는 오케스트레이션 스킬. 다른 스킬이 *산출물을 만든다면*, 본 스킬은 **팀과 실행 구조를 산출물로 만든다** — 누가(에이전트), 어떤 순서로(의존성 체인), 어떤 경계에서(쓰기 경계·핸드오프) 일하는지를 승인 가능한 구성안 1장으로 낸다.

## 0. 지위 — 파이프라인 포지션

```
jc-prompt-builder ──▶ jc-orchestrator ──▶ 매핑 스킬들(mice-*·jc-*) ──▶ jc-redteam
  (최상류: 지시의       (팀 구성·실행 설계)      (개별 산출물 생성)        (최하류: 검증)
   브리프화 게이트)
```

- **운영지침 §8 에이전트 팩토리의 실행체** — 상세(에이전트 카탈로그·킥오프 템플릿·핸드오프 규약·구성안 출력 형식)의 SoT는 본 스킬이 소유한다. 단, **5단계 골격·승인 게이트라는 계약 자체의 SoT는 운영지침**이다(지침은 발동 선언 + 골격 + 폴백 조항을 유지하며, 폴백 조항은 삭제 불가 항목).
- **전 서피스 공통 단일 실행체** — Chat·Cowork·Code 어디서든 동일 프로토콜. jc-prompt-builder처럼 서피스별 이원화하지 않는다(팩토리는 저빈도 발동).
- 본 스킬로 향하는 지시도 실행 전 jc-prompt-builder 브리프를 거친다(선행 게이트). 브리프가 승인되면 그 필드(목표·산출물·제약)를 §2 프로토콜 1단계의 기입력으로 승계한다.

## 1. 발동 판정

다음 중 **2개 이상** 해당하면 팩토리를 발동한다. 1개만 해당하고 모호하면 사용자에게 발동 여부를 확인한다.

1. **이질 역량 3+** — 전략·리서치·콘텐츠·디자인·데이터·코드 등 서로 다른 아키타입 3개 이상이 필요
2. **산출물 다수** — 독립 산출물 3개 이상, 또는 Phase가 나뉘는 다단계 구조
3. **세션·서피스 전환** — Cowork 병렬·Code 서브에이전트 등 실행 환경 설계가 필요

**단독 발동 예외** — 신규 Claude Project 세팅·Project Instructions 발행이 필요한 지시는 기준 충족 수와 무관하게 발동한다(지침 §8 발동 선언 "새 프로젝트 설명 시"와 정합).

**미발동 케이스** (팀이 아니라 다른 장치가 정답인 경우):

| 상황 | 올바른 처리 |
|------|------------|
| 단일 스킬로 끝나는 작업 (제안서 1건, 견적 1건) | 해당 전용 스킬 단독 실행 |
| 단순 고밀도 작업의 N턴 분할 | 운영 규칙의 3턴 분할(기획→빌드→검수) — 팀 구성 아님 |
| 완성물 검증만 필요 | jc-redteam 직행 |
| "이번만 팀 없이 빨리" 류 우회 요청 | 복합성 기준 충족 시 최소 구성(2에이전트)이라도 제안 — 무설계 진행은 재작업 리스크를 사용자 승인으로만 감수 |

## 2. 팩토리 프로토콜 — 5단계 (지침 §8 이관 정본)

```
① 성격 분석   : 작업의 역량 축·산출물·의존성·환경을 분해 (브리프 승계 입력)
② 조합 제안   : 에이전트 카탈로그(§3)에서 최적 조합 + 수행 순서 도출
③ 역할 정의   : 에이전트별 역할·전문성·입출력 계약·범위 확정
④ 승인 게이트 : 구성안(§7 형식) 제시 → 사용자 승인 후에만 진행 (무승인 실행 금지)
⑤ 환경별 실행 : Chat=순차 / Cowork=병렬 / Code=서브에이전트 병렬 (§4 킥오프 템플릿)
```

- ④에서 승인과 함께 **Project Instructions 저장 텍스트**를 발행한다(§7). PI는 운영지침을 상속하며 포인터로만 참조한다 — 지침 내용의 중복 기재 금지(드리프트 방지).
- 구성안 수정 요청 시 해당 항목만 교체해 재제시한다(전체 재작성 금지).
- **② 조합 제안 시 회피할 안티패턴** (멀티 에이전트 설계 반복 실패 패턴):
  - *과분할* — 한 스텝이 한 산출물보다 잘게 쪼개져 핸드오프 비용이 작업 이득을 초과. 에이전트당 독립 산출 1개 입도로 병합한다
  - *순차화된 병렬* — 의존성이 없는데 직렬로 늘어놓아 실행이 지연. §5 병렬 스텝 탐지로 독립 노드를 병렬 승격한다
  - *모호한 핸드오프* — 입력 경로·출력 계약 없이 "앞 단계 참고"로 넘겨 컨텍스트 격리 환경에서 재작업 유발. §5 규약 1·2로 사전 차단한다

## 4. 환경별 실행 모델 — 정직한 실행 의미론

각 환경의 실행 방식은 아래가 **사실 그대로**다. 실제 동작 이상으로 포장하지 않는다("병렬 AI 팀" 과장 금지 — 2026-05 html-pt 실증 교훈).

| 환경 | 실행 의미론 | 킥오프 템플릿 |
|------|------------|--------------|
| **Chat** | 단일 컨텍스트에서 **역할을 순차 전환**. 에이전트 = 관점 프레임이며 진짜 격리가 아니다. 턴당 1역할 권장 | [`references/kickoff-chat.md`](references/kickoff-chat.md) |
| **Cowork** | 메인 세션이 다수 작업 스레드를 **파일 경계로 병렬 관리**. 에이전트별 쓰기 경로 분리 필수 | [`references/kickoff-cowork.md`](references/kickoff-cowork.md) |
| **Code** | 서브에이전트는 **동시 호출 가능하나 컨텍스트 격리** — 에이전트 간 실시간 양방향 피드백 불가. 병렬은 의존성 없는 노드에만 성립 | [`references/kickoff-code.md`](references/kickoff-code.md) |

- 어떤 환경이든 킥오프에 **쓰기 경계·완료 신호·승인 포인트**를 명문화한다. 경계 변경은 킥오프 공식 개정으로만 한다(암묵 변경 금지).
- 위임 모델 선택: 복잡 판단=주력 최상위 계열 / 문서·데이터 가공=중간 계열 / 추출·변환=경량 계열. 구체 모델·버전은 하드코딩하지 않는다(RULE-VERSION-FACTS) — 시점별 권장표는 사용자 운영 체계(지침 §6·메모리 조합표)가 소유. Code에서 이 원칙을 물리 장치로 강제하려면 code-conductor 프리셋(§6.2)을 설치한다.

## 5. 핸드오프 규약 (요지)

정본: [`references/handoff-protocol.md`](references/handoff-protocol.md). 핵심 5칙:

1. **입력 명시 의무** — 에이전트 호출 시 읽어야 할 파일 경로를 반드시 명시한다(컨텍스트 격리 전제. "앞 단계를 참고해"는 금지 표현)
2. **출력 계약** — 산출 파일의 경로·파일명·형식을 사전 계약하고 준수한다
3. **의존성 체인 판정** — 선행 산출이 입력이면 순차, 독립이면 병렬 가능. 판정 근거를 구성안에 남긴다
   - **병렬 스텝 탐지**: 두 스텝이 ⓐ 같은 파일을 쓰지 않고 ⓑ 서로의 출력을 입력으로 삼지 않으면 병렬 후보다. 공통 기반(인터페이스·토큰·스키마) 스텝을 먼저 완료한 뒤 그 위에 얹히는 독립 구현들을 병렬 디스패치한다. 쓰기 경로가 겹치면 병렬에서 제외한다(§4 "의존성 없는 노드에만 성립"과 정합)
4. **완료 신호** — Phase·에이전트 완료 시 PROGRESS.md(또는 합의된 신호 파일)에 1줄 로그
5. **ChainPayload/v1** — 구조화 데이터(견적·KPI·분석 결과) 핸드오프는 봉투 규약 적용. 정본: `jc-design-system`의 chaining-protocol

## 7. 구성안·PI 발행 형식 (고정)

④ 승인 게이트에서 항상 아래 형식으로 낸다:

```
--- [프로젝트명] 에이전트 구성안
투입 에이전트: <아키타입/프리셋 + 각 1줄 역할>
수행 순서:    <의존성 체인 — 순차/병렬 구간 명시>
통합 방식:    <메인 검수·핸드오프 규약·완료 신호>
Project Instructions 저장 텍스트:
[복사용 블록 — 운영지침 상속 선언 + 본 구성안 포인터 + 프로젝트 고유 규칙만]
---
```

- PI 복사용 블록에는 **프로젝트 고유 규칙만** 넣는다. 운영지침·본 스킬 내용을 복붙하지 않는다(단일 소유).

## 8. 공통 룰 (정본 참조)

- **RULE-NO-COMPANY** — 본 스킬 문서·템플릿·프리셋에 특정 회사명·실명 하드코딩 금지. 식별정보는 `{{client_company}}` 등 외부 주입 변수로만. 정본: `jc-design-system/references/shared-rules.md#RULE-NO-COMPANY`
- **RULE-VERSION-FACTS** — 모델·제품 등 시점 종속 팩트는 기록 직전 실검증 + 검증일 병기, 계열명 우선. 정본: 동일 shared-rules.md
- 디자인 토큰: 본 스킬 산출물(구성안·PI)은 텍스트 게이트라 **토큰 비소비**. 단, 프리셋 내 디자인 계열 에이전트는 jc-design-system SoT 앵커를 따른다(하드코딩 금지)
- 검증 연결: 고부담 산출물을 내는 팀 구성에는 리스크 아키타입(jc-redteam)을 기본 포함 권장

## 9. 유지보수

- 스킬 라이브러리 변동(신규·통폐합) 시 §3 카탈로그의 연결 스킬을 갱신하고 `version` 범프
- jc-prompt-builder의 routing-map·description-registry 재생성 시 본 스킬 편입 확인
- 5단계 골격·승인 게이트 자구가 지침과 어긋나면 **지침이 SoT — 본 스킬 쪽을 수정**한다. 카탈로그·킥오프·핸드오프·출력 형식 등 상세가 어긋나면 본 스킬이 SoT — 지침·타 문서 쪽을 수정한다
