# jc-prompt-builder

러프한 작업 지시를 **실행 직전에 '업그레이드 브리프'로 증강**하는 default-on 상시 레이어. 다른 스킬이 *산출물을 생성*한다면, 본 스킬은 **지시 자체를 첫 산출물로 만든다** — 의도 왜곡 0을 유지한 채 맥락·스펙·성공 기준·가정을 붙여, 첫 실행에서 재작업 없는 결과가 나오게 한다. 본 스킬은 매핑 스킬을 대체하지 않는 **선행 게이트**다: 다른 스킬이 트리거되는 지시라도 브리프를 먼저 거친 뒤 그 스킬로 라우팅한다.

## 0. 지위 — 서피스별 가동 상태

| 서피스 | 상태 | 맥락 소스 |
|--------|------|----------|
| 챗 | 운영지침 §3으로 **기가동** — 본 스킬 설치 대상 아님 | (운영지침 소관) |
| **Code** | 본 스킬 담당 | CLAUDE.md · PROGRESS.md · 레포 |
| **Cowork** | 본 스킬 담당 | 작업폴더 |

- 챗 운영지침 §3과 본 스킬은 **동일 정본(내장 프로토콜 v1, §4)**을 공유한다. 서피스가 달라도 브리프의 필드·체크리스트는 같다.
- 챗에서 이미 브리프·승인을 거친 지시가 Code/Cowork로 넘어온 경우, 브리프를 **재작성하지 않고 승계**한다(가정 필드만 새 환경 맥락으로 재확인).

## 1. 성격 — default-on · 예외 · 옵트아웃

- **기본 가동(default-on)**: 실질 작업 지시(산출물 생성·분석·개발·다단계 작업)에는 항상 브리프를 거친다. 사용자가 요청할 때만 켜지는 스킬이 아니다.
- **예외(자동 스킵)**: 단순 대화·즉답 — 사실 확인, 단답 조회, 짧은 의견, 파일 한 개 열람처럼 *산출물이 없고 잘못돼도 되돌릴 비용이 0에 가까운* 턴.
- **옵트아웃**: 사용자가 **"그대로 실행"**(또는 동급 표현: "바로 해줘", "브리프 생략")을 명시하면 브리프 없이 즉시 실행한다. 옵트아웃은 **해당 지시 1건**에만 적용하며, 세션 전체 옵트아웃은 사용자가 별도로 선언할 때만 유지한다.

판정이 모호하면 세 가지 중 하나라도 해당할 때 브리프를 거친다: ① 실행에 수 분 이상 걸리는 작업량 ② 파일 생성·수정 발생 ③ 다단계(3스텝 이상) 진행.

## 2. 게이트 — 브리프 + 범위 [A/B/C] 한 카드, 승인 1회

브리프는 기존 운영 규칙의 **범위 판단 [A/B/C] 제시와 통합해 한 카드**로 낸다. 승인 절차가 늘어나지 않는다 — 원래 있던 승인 1회에 브리프가 실리는 것이다. 브리프 따로, 범위 따로 두 번 묻는 것을 금지한다.

**범위 [A/B/C] 정의** (운영 규칙 정본과 동일 스케일 — 서피스 무관 자가완결):

- **[A]** 현재 세션에서 단발 진행 (단일 산출물·저부담)
- **[B]** 현재 세션에서 N턴 분할 (다단계·검토 필요 → **분할 계획을 카드에 함께 제시**)
- **[C]** 새 세션 / 새 프로젝트 권장 (컨텍스트 초과·독립 작업·에이전트 전환)

**카드 표준 형식** (전/후 실사례는 [`references/briefing-examples.md`](references/briefing-examples.md)):

```
📋 업그레이드 브리프
목표      : <의도 1문장 재진술>
산출물    : <형태·분량·포맷·저장 위치> (매핑 스킬: <skill> / 독자: <대상>)
맥락 반영  : ① <핵심> (출처: <소스>) ② … ③ …   ※ 최대 3
성공 기준  : 1) … 2) … (3) …)
제약      : <운영 규칙·형식·톤 자동 반영분 + 소스 내 금지·조건 조항>
예시 쌍   : (고밀도 작업 시) ✅ <긍정 1줄> / ❌ <부정 1줄>
가정      : A1) … A2) …   ※ 원문에 없던 추론 채움 전부 — 승인 시 확정
──────────────────────────────
범위 [B] 현재 세션 3턴 분할 (Turn1 기획 → Turn2 빌드 → Turn3 검토)
권장 모델: <계열명> (references/model-guide.md 기준)
→ 승인 / 필드 수정 / 그대로 실행
```

- **승인 방식**: 서피스가 버튼형 선택지를 지원하면 버튼(승인·필드 수정·그대로 실행)으로, 아니면 짧은 텍스트 응답으로 받는다.
- **선택지 3종의 동작**: ① **승인** — 가정 필드가 확정 팩트로 전환되고 실행 시작. ② **필드 수정** — 해당 필드만 교체해 재제시(전체 재작성 금지). ③ **그대로 실행**(사후 옵트아웃) — 브리프·가정을 폐기하고 러프 원문만으로 즉시 실행. 가정은 확정되지 않으며 재작업 리스크는 사용자 선택이다.

## 3. 환경별 맥락 소스 — 수집 상한: 핵심 3개

| 서피스 | 소스 우선순위 | 요지 |
|--------|-------------|------|
| Code | ① CLAUDE.md(및 그것이 가리키는 SoT 문서) ② PROGRESS.md ③ 지시 관련 레포 파일 실측 | 지침 → 진행 상태 → 코드/문서 순 |
| Cowork | ① 작업폴더 `_INDEX.md`(있으면) ② 폴더 위계·표준 구조 ③ 최근 수정 파일 | 요약 → 구조 → 실물 순 |

- **과적재 금지**: 수집한 것 중 **브리프에 주입하는 것은 상위 3개까지**. 선별 기준·출처 명기 형식·소스별 상세 절차는 [`references/context-sources.md`](references/context-sources.md).
- 맥락이 산출물 스펙을 바꾸면 '산출물' 필드에, 제약을 만들면 '제약' 필드에 반영하고 각각 출처를 남긴다.

## 4. 내장 프로토콜 v1 — 원문

> 아래 두 블록은 챗(Fable 5)이 저작한 프로토콜 원문이다(N5 최종 스펙 v3, 2026-07-03 수록). **재증류(§8) 전까지 자구를 수정하지 않는다** (자구 동결은 본문 텍스트 기준이며 마크다운 강조 서식은 포함하지 않는다).

◇ 브리프 6필드: 목표(의도 1문장 재진술) / 산출물(형태·분량·포맷·매핑 스킬) / 맥락 반영(주입 핵심 최대 3, 출처 명기) / 성공 기준(2~3) / 제약(운영 규칙·형식·톤 자동 반영) / 가정(추론 채움 전부 — 승인 시 확정) → 말미에 범위 [A/B/C] + 권장 모델 병기

◇ 체크리스트 8항: ① 의도 재진술 후 원문 대조(왜곡 0) ② 환경 소스에서 맥락 상위 3개만 주입(과적재 금지) ③ 산출물 스펙 명시(형태·분량·포맷·독자) ④ 성공 기준·완료 조건 정의 ⑤ 제약·금지 반영(추측 금지·검증 게이트·표기 규칙) ⑥ 고밀도 작업 시 긍정·부정 예시 1쌍 삽입 ⑦ 프로세스 매핑(3턴 분할·해당 스킬 워크플로우) ⑧ 가정 분리 표기 필수 — 원문에 없던 것은 전부 '가정'

### 4.1 운용 해설 (원문을 실무로 옮기는 기준)

| 항 | 실무 기준 |
|----|----------|
| ① 의도 재진술 | 재진술 문장을 쓴 뒤 사용자 원문과 나란히 대조한다. 원문에 없는 목적어·수식이 끼어들면 왜곡 — '가정'으로 이동시킨다 |
| ② 맥락 ≤3 | §3 소스에서 수집 → 선별 기준([`context-sources.md`](references/context-sources.md) §3)으로 상위 3개만. 4개째부터는 버린다. 단, 소스에서 발견한 **금지·조건 조항**(백업 선행·승인 게이트 등)은 3개 상한과 무관하게 '제약' 필드로 직행한다 *(원문 확장분 — §8 재증류 시 원문 반영 검토)* |
| ③ 산출물 스펙 | 형태(파일/카드/텍스트)·분량·포맷(확장자)·독자 4요소를 모두 채운다. 파일 산출물이면 **저장 위치·파일명**, 외부 공개물이면 **전달·배포 방식**까지 스펙의 일부다. 매핑 스킬은 [`routing-map.md`](references/routing-map.md)로 결정 |
| ④ 성공 기준 | "무엇이 되면 완료인가"를 검증 가능한 문장 2~3개로. 측정 불가 기준("좋게", "잘")은 금지. 탈출구(예: "재현 불가 시 보고")를 두면 **그 이후 행동(중단/조건부 진행)까지 정의**한다 |
| ⑤ 제약·금지 | 운영 규칙 자동 반영분: 추측 금지(팩트 기반), 검증 게이트(고부담 산출물은 jc-redteam), 표기 규칙(RULE-* 해당분) + ②에서 직행한 소스 내 금지·조건 조항 *(후자는 원문 확장분)*. 사용자가 말 안 해도 넣는다 |
| ⑥ 예시 1쌍 | 고밀도 작업(문서·데크·대시보드·코드 등 스타일 자유도가 큰 산출)에만 — 카드의 '예시 쌍' 행에 삽입한다. 유형별 기성 쌍: [`briefing-examples.md`](references/briefing-examples.md) §3 |
| ⑦ 프로세스 매핑 | 고밀도 산출물은 3턴 분할(기획→빌드→검토), 매핑 스킬이 있으면 그 스킬의 표준 워크플로우를 브리프에 명기 |
| ⑧ 가정 분리 | 원문에 없던 것은 전부 '가정' 필드로. 본문(목표·산출물·맥락)에 섞어 넣는 순간 왜곡이다. 승인이 가정을 팩트로 바꾼다. **역참조 규칙**: 가정에 의존하는 본문 서술에는 해당 번호를 병기("KPI 대시보드 *(A1)*")하고 확정 톤으로 재서술하지 않는다 — 가정을 분리해 놓고 본문에서 기정사실처럼 쓰면 분리의 실효가 사라진다 |

## 5. 표준 워크플로우

```
[작업 지시 수신]
    ↓
[스킵 판정]  단순 대화·즉답? ──────────→ 예: 브리프 없이 응답 (§1)
            "그대로 실행" 명시? ───────→ 예: 즉시 실행 (사전 옵트아웃)
    ↓ 아니오
[맥락 수집]  서피스별 소스에서 핵심 ≤3 (§3)
    ↓
[브리프 저작] 6필드 작성 → 체크리스트 8항 자가 점검 (§4)
    ↓         매핑 스킬 결정: references/routing-map.md
[한 카드 제시] 브리프 + 범위 [A/B/C] + 권장 모델 (§2)
    ↓
[승인 1회]   승인 → 가정 확정, 실행 개시
            필드 수정 → 해당 필드만 교체 후 재제시
            그대로 실행 → 브리프·가정 폐기, 원문대로 실행 (사후 옵트아웃, §2)
    ↓
[실행]      매핑 스킬 워크플로우 · 3턴 분할 등 프로세스 매핑대로.
            매핑 스킬이 자체 컨텍스트 수집 단계를 가지면(예: jc-doc-coauthor Stage 1)
            승인된 브리프 필드를 그 단계의 기답변으로 승계하고, 브리프가 못 채운 갭만 묻는다.
            매핑 스킬의 진입 제안(프로세스 수락 질문)은 브리프 승인이 대체한다.
```

## 6. 경계 — 역할 분리 (본 스킬 = '프롬프트 내용 증강' 전담)

| 인접 기능 | 소재 / 담당 영역 | 본 스킬과의 경계 |
|----------|----------------|----------------|
| 자동 세팅 | 챗 운영지침 소관 (무표기 적용) — Code/Cowork에는 별도 실체 없음 | 추론 깊이·검색·프레임워크·스킬 **선택**은 세팅의 영역. 본 스킬은 지시의 **내용**을 증강 — 세팅을 설명하지도, 대신 정하지도 않는다 |
| 에이전트 팩토리 | 챗 운영지침 소관 개념 — Code/Cowork에 전용 스킬 없음 | 멀티 에이전트 **팀 구성** 지시가 오면 본 스킬은 브리프만 작성하고 매핑은 '없음(직접 수행)', 실행 방식은 가정 필드로 승인받는다([`routing-map.md`](references/routing-map.md) §2) |
| jc-doc-coauthor | 문서 **공동작성 프로세스** | 코오서는 N턴에 걸쳐 문서를 함께 쓴다. 본 스킬은 실행 전 **1카드 게이트** — 코오서로 넘어가는 지시조차 브리프는 1장으로 끝낸다. 승인된 브리프 필드(독자·목표·제약)는 코오서 Stage 1의 기답변으로 승계하고, 코오서는 브리프가 못 채운 갭만 묻는다(§5 실행 단계) |
| jc-skill-creator | 스킬 제작 메타 작업 | 스킬을 만드는 일 자체는 creator. 본 스킬은 그 지시("스킬 만들어줘")의 브리프만 |
| jc-redteam | 완성 산출물의 적대적 검증 | redteam은 **최하류**(완성물 공격), 본 스킬은 **최상류**(시작점 강화). 고부담 산출물이면 브리프 '제약' 필드에 redteam 게이트를 명기해 연결한다 |

브리프의 '산출물' 필드가 매핑 스킬을 지정하지만, 본 스킬은 그 스킬을 **대체하지 않는다** — 결정하고 넘길 뿐, 산출물 생성은 각 전용 스킬의 일이다.

## 7. 공통 룰 (정본 참조)

- **RULE-NO-COMPANY** — 브리프·예시·본 스킬 문서에 특정 회사명·실명·부서명 하드코딩 금지. 식별정보는 `{{client_company}}` 등 외부 주입 변수로만. 정본: `jc-design-system/references/shared-rules.md#RULE-NO-COMPANY`
- **RULE-VERSION-FACTS** — 권장 모델 등 시점 종속 팩트는 기록 직전 실검증 + 검증일 병기, 계열명 우선. 정본: `jc-design-system/references/shared-rules.md#RULE-VERSION-FACTS`. 적용 위치: [`references/model-guide.md`](references/model-guide.md)
- 디자인 토큰: 본 스킬의 산출물(브리프 카드)은 대화 내 텍스트라 **디자인 토큰 비소비** — SoT 앵커 대상 없음. ChainPayload 봉투도 쓰지 않는다(브리프는 파일이 아니라 게이트).

## 8. 유지보수 — 모델 세대 변경 시 프로토콜 재증류

프로토콜 v1은 Claude 5 세대(Fable 5)의 지시 해석 특성을 전제로 증류됐다. **주력 모델 세대가 바뀌면 재증류한다** (분기 점검 주기와 연동, RULE-VERSION-FACTS).

1. 러프 지시 5종 전/후 비교를 새 모델로 재실행 — 브리프 효과가 유지되는지 실측
2. 체크리스트 8항의 유효성 재평가 (새 모델이 자동으로 잘하게 된 항목은 축소, 새 실패 모드는 항목 추가). §4.1의 '원문 확장분' 태그 항목의 원문 흡수 여부도 이때 결정
3. [`model-guide.md`](references/model-guide.md) 웹 재검증 + 검증일 갱신
4. description 실측 스냅숏 재생성 — `python scripts/build_routing_map.py --skills-dir <스킬 라이브러리 루트>` (산출물은 [`description-registry.md`](references/description-registry.md)) → registry diff를 확인해 [`routing-map.md`](references/routing-map.md) §2·§3 해당 행을 **수동 갱신**
5. `version` 범프(프로토콜 자구 변경 시 minor 이상) + 원문 블록(§4) 교체 및 저작 주체·일자 갱신
