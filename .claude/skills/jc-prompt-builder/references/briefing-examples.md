# Briefing Examples — 브리프 전/후 실사례 + 유형별 예시 쌍

체크리스트 ⑥(고밀도 작업 시 긍정·부정 예시 1쌍 삽입)의 기성 재료와, 브리프가 실제로 무엇을 바꾸는지 보여주는 전/후 사례. 모든 예시는 RULE-NO-COMPANY(정본: `jc-design-system/references/shared-rules.md#RULE-NO-COMPANY`)를 따른다 — 식별정보는 `{{client_company}}` 등 슬롯으로만.

## 1. 전/후 사례 A — 러프 지시 → 브리프 (분석 보고)

**러프 원문**: "이번 행사 결과 정리해줘"

**브리프 적용 후**:

```
📋 업그레이드 브리프
목표      : {{event_name}} 결과를 보고 가능한 형태로 정리한다 (형태·독자는 A1·A2)
산출물    : KPI 대시보드 (A1), 단일 HTML 1파일 → 50_outputs/{{event_name}}-결과.html
          (매핑 스킬: mice-dashboard / 독자: 발주처 의사결정자 (A2) / 전달: 송부용 파일)
맥락 반영  : ① 등록·참가·매출 실측치는 ops 폴더 결과 파일 (출처: 40_ops/결과데이터.xlsx)
          ② 발주처가 작년 대비 성장률을 요구한 이력 (출처: _INDEX.md 상태 블록)
          ③ 송부용 — 외부 톤, 인쇄 배포 가능해야 함 (출처: 사용자 발언(금일))
성공 기준  : 1) 핵심 KPI가 첫 화면에서 읽힘 — 어떤 지표를 헤드라인으로 올릴지는 Turn1에서 확정
          2) 전년 대비 증감이 모든 지표에 병기 3) 인쇄(PDF) 출력 시 라이트 모드 강제
제약      : 수치는 결과 파일 실측만(추측 금지) · RULE-PRINT-LIGHT · 식별정보 외부 주입
          · 매출·수익 수치의 외부 공개 여부는 Turn1에서 확인 후 포함(A3)
예시 쌍   : ✅ 첫 화면에서 핵심 KPI가 읽히고 모든 수치에 전년 대비 기준이 붙는다
          ❌ 차트 10개가 같은 크기로 나열되고 어떤 숫자가 좋은지 나쁜지 알 수 없다
가정      : A1) '정리'의 의도는 산문 보고서가 아니라 대시보드 (원문 불명시)
          A2) 독자는 발주처 (내부 보고면 톤 변경 필요)
          A3) 매출 수치도 발주처 공개 가능 (민감하면 제외 구성 필요)
──────────────────────────────
범위 [B] 현재 세션 3턴 분할 (Turn1 지표 설계 → Turn2 빌드 → Turn3 검토)
권장 모델: Sonnet 계열 (High — 표준 산출, model-guide.md)
→ 승인 / 필드 수정 / 그대로 실행
```

**무엇이 달라지나**: 러프 원문만으로는 산문 요약이 나올 확률이 높다. 가정 A1이 그 갈림길을 승인 전에 드러낸다 — 사용자가 "아니, 텍스트로"라고 한마디만 하면 재작업 없이 방향이 바뀐다.

**표기 주의(실측 교훈)**: 가정에 의존하는 본문 서술에는 위처럼 **(A1) 역참조를 병기**한다. 가정 필드에 분리해 놓고 목표·산출물·성공 기준에 같은 내용을 확정 톤으로 재서술하면, 승인자가 카드를 훑을 때 갈림길이 아니라 확정 스펙으로 읽혀 분리의 실효가 사라진다. 또 민감할 수 있는 데이터(매출 등)를 성공 기준에 못박지 말 것 — A3처럼 공개 적절성 자체를 가정으로 노출한다.

## 2. 전/후 사례 B — 러프 지시 → 브리프 (개발 작업)

**러프 원문**: "회의록 스킬에 시리즈 기능 버그 있는 것 같은데 고쳐줘"

**브리프 적용 후**:

```
📋 업그레이드 브리프
목표      : 회의록 스킬의 시리즈(회차 누적) 기능 결함을 실측·수정한다
산출물    : 해당 스킬 파일 수정 + 결함 원인 1문단 보고 (매핑 스킬: 없음(직접 수정) / 독자: 기획자님)
맥락 반영  : ① 시리즈 상태는 window.storage 영속화 구조 (출처: 해당 스킬 SKILL.md)
          ② 최근 v2.1.0에서 산출 포맷 변경 이력 (출처: SKILL.md 버전 히스토리)
성공 기준  : 1) 재현 절차로 결함이 실제 재현됨 — 재현 불가면 근거 보고 후 **수정 없이 중단**(증상 재확인 대기)
          2) 수정 후 동일 절차에서 정상 동작 확인
제약      : 재현 전 수정 금지(추측 금지) · 다른 스킬 파일 변경 없음
          · 수정 전 백업 선행 (출처: 진행 문서의 백업 필수 조항 — 맥락 상한과 무관하게 직행)
예시 쌍   : ✅ 변경이 지시된 범위 안에서만 일어나고 기존 코드 관례를 따른다
          ❌ 요청 안 한 리팩터링이 섞여 diff가 부풀고 주변과 다른 스타일이 등장한다
가정      : A1) '버그'는 회차 누적이 안 쌓이는 증상으로 추정 — 증상 재확인 필요
──────────────────────────────
범위 [A] 현재 세션 단발 진행
권장 모델: Sonnet 계열 (High — 표준 코딩, model-guide.md)
→ 승인 / 필드 수정 / 그대로 실행
```

**무엇이 달라지나**: "고쳐줘"만 받으면 증상 추정 → 추정 수정으로 직행하기 쉽다. 성공 기준 1이 "재현 먼저"를 강제하고, 가정 A1이 증상 인식의 어긋남을 승인 단계에서 잡는다.

**표기 주의(실측 교훈)**: ① 산출 형태는 환경 실측에 맞춘다 — git이 없는 폴더에서 "수정 커밋"이라 쓰면 실행 불가능한 스펙이다. ② 진행 문서의 거버넌스 조항(백업 선행·승인 게이트)은 맥락 3개와 경쟁시키지 말고 '제약'으로 직행시킨다(context-sources.md §3 예외). ③ 성공 기준의 탈출구("재현 불가면 보고")는 그 **이후 행동**(중단인지 조건부 진행인지)까지 정의해야 교착·재량 복귀를 막는다.

## 3. 유형별 긍정·부정 예시 쌍 (체크리스트 ⑥ 삽입용)

고밀도 작업의 브리프 '제약' 필드 아래에 붙이는 1쌍. 산출물 유형에 맞는 것을 골라 쓰고, 상황에 맞게 구체화한다.

### 문서 (기획서·보고서·메모)

- ✅ **긍정**: "결론을 첫 문단에 두고, 각 주장 뒤에 근거(출처·수치)가 한 몸으로 붙는다"
- ❌ **부정**: "배경 설명 3문단 뒤에야 본론이 시작되고, '~로 기대된다'류 근거 없는 전망이 섞인다"

### 슬라이드·데크 (제안서·스폰서 데크)

- ✅ **긍정**: "슬라이드당 메시지 1개, 헤드라인만 읽어도 스토리가 이어진다"
- ❌ **부정**: "불릿 7개가 본문 폰트로 빼곡하고, 헤드라인이 '개요'·'현황' 같은 라벨이다"

### 대시보드·시각화

- ✅ **긍정**: "첫 화면에서 핵심 KPI가 읽히고, 모든 수치에 비교 기준(전년·목표 대비)이 붙는다"
- ❌ **부정**: "차트 10개가 같은 크기로 나열되고, 어떤 숫자가 좋은 건지 나쁜 건지 알 수 없다"

### 코드·개발

- ✅ **긍정**: "기존 코드의 명명·구조 관례를 따르고, 변경은 지시된 범위 안에서만 일어난다"
- ❌ **부정**: "요청 안 한 리팩터링이 섞여 diff가 부풀고, 주변 코드와 다른 스타일이 등장한다"

### 커뮤니케이션 글 (메일·공지·업데이트)

- ✅ **긍정**: "받는 사람이 해야 할 행동이 첫 세 줄 안에 나온다"
- ❌ **부정**: "인사·경과 설명이 길고, 요청 사항이 마지막 문단에 숨어 있다"

## 4. 브리프 자체의 긍정·부정 (자가 점검용)

- ✅ **좋은 브리프**: 6필드가 전부 채워지되 각 필드가 1~3줄. 가정이 원문과 분리돼 있고, 승인자가 30초 안에 읽고 판단할 수 있다.
- ❌ **나쁜 브리프**: 맥락이 4개 이상 들어가 카드가 화면을 넘어간다 / 가정이 목표·산출물 필드에 사실처럼 섞여 있다 / 성공 기준이 "고품질로", "잘 정리되게"처럼 검증 불가능하다 / 범위와 브리프를 두 카드로 나눠 승인을 두 번 받는다.
