# 진행 규약 — 요청 하나 = 스레드 하나 · 체크리스트 · 기획안 1회 확인 → 빌드 → 검수

(파일명은 하위호환으로 `turn-protocol.md` 유지. 2026-10-05 v1.1.0에서 턴 분할·범위 게이트를 폐지하고 이 규약으로 교체했다.)

---

## 1. 기본 흐름

```
요청 1건 접수 ─ 스레드(세션) 1개 배정 ─ 체크리스트 게시
   │
   ├ 일반 작업(되돌릴 수 있음: 초안·파일·분석·코드 수정)
   │     → 합리적 기본값으로 바로 진행, 고른 기본값을 한 줄로 밝힘 → 결과 + 검수
   │
   ├ 고밀도 산출물(덱·장문 문서·대시보드·여러 파일 빌드)
   │     → 기획안(구성·핵심 메시지) 1회 확인 → 빌드 → 검수(jc-redteam)
   │
   └ 되돌릴 수 없는 작업(외부 발송·게시·삭제·배포·결제)
         → 그 단계 직전에만 승인 요청. 나머지는 계속 진행
```

- **요청 하나 = 스레드 하나.** 한 스레드에서 다른 요청을 섞지 않는다. 새 요청은 새 스레드(또는 새 세션)로 열고, 이어받을 맥락은 PROGRESS.md·파일로 넘긴다.
- **체크리스트로 진행을 보인다.** 첫 응답에 단계 목록(✓ 완료 · ✱ 진행 중 · ○ 대기)을 내고, 단계가 끝날 때마다 같은 목록을 갱신한다. 단계마다 "진행할까요?"를 묻지 않는다.
- **확인은 1회.** 고밀도 산출물만 기획안을 한 번 보여 주고, 승인 후에는 빌드·검수까지 끊지 않는다. 기획자님이 "바로 해줘"라고 하면 기획안 확인도 생략한다.
- **검수는 마지막에 한 번.** `jc-redteam`(Quick Strike 또는 Deep Audit)로 판정하고, 조건부 보완이면 패치 → 영향 경로 재검증 → 보고.
- 폐지: 3턴 분할(1 기획 → 2 빌드 → 3 검수를 턴 단위로 끊기), [A]/[B]/[C] 범위 게이트, "실행 전 브리프" 게이트, 단계별 확인.

## 2. 서피스 분업 (선택)

Cowork에서 기획하고 Code에서 빌드하는 분업은 여전히 쓸 수 있다. 다만 턴 번호로 계약하지 않는다.

| 구간 | 서피스 | 산출 |
|------|--------|------|
| 기획 | Cowork 챗 또는 같은 Code 세션 | SPEC 정본 · 결정 D번호 · (분업 시) 착수 지시문 `docs/code-brief-<n>.md` |
| 빌드 | Code 세션 (서브에이전트 병렬 가능) | 산출물 · 게이트 수치 · 체크아웃 보고 |
| 검수 | jc-redteam (또는 Cowork 챗) | 판정(Critical/Major/Minor) → 조건부 보완이면 패치 지시문 `code-brief-<n>.1` |

- 결정 후 곧바로 빌드하는 압축형이 기본이다: 같은 세션에서 기획안 → 결정 → 빌드 → 검수. 결정 표는 CLAUDE.md에 그대로 추가한다.
- 분업은 서피스가 바뀔 때(Cowork ↔ Code, 머신 교체)만 쓴다.

## 3. 착수 지시문 (code-brief) 필수 절

템플릿: `assets/templates/code-brief.md.template`.

| 절 | 내용 |
|----|------|
| 세션 설정 | 작업 폴더(= 세션, 다른 폴더 쓰기 금지) · 권장 모델·사고 수준(서브에이전트별 차등 가능, `SKILL.md §5`) · 언어 |
| 0 체크인 | 2파일+SPEC 존재 확인 → 없으면 부록에서 그대로 생성 → 지시문 자체를 `docs/code-brief-<n>.md`로 저장 → 변경 불가 계약(결정 D번호·작업 규칙) 인지 → 착수 조건 미충족 시 대체안 |
| 1 목표 | SPEC 한 줄 정의 구현 |
| 2 산출물과 경로 | 표: 경로 · 내용 (전부 생성) |
| 3 계약 동결 | 데이터 계약·인터페이스·스키마를 빌드 전에 문서로 고정. 서브에이전트는 이 파일만 본다 |
| 4 실행 구조 | 서브에이전트 N 병렬(파일 단위 겹침 없이) + 메인 병합. 각 에이전트의 입력 파일·출력 경로 |
| 5~7 규격 | 가상 데이터·기술 규칙·가이드 규격 등 프로젝트별 |
| 8 품질 게이트 | 메인이 직접 실행하고 수치로 보고: 빌드 재현성 · 테스트 · 실렌더(탭·쓰기 경로 전수) · 정적 검사 · 금칙어 grep · jc-redteam |
| 9 체크아웃 | PROGRESS 갱신 + 보고 블록 출력 |
| 10 금지 | 쓰기 경계 밖 · SPEC 이탈 · 하드코딩 · 외부 라이브러리 · 대화상자 등 |

부록 A·B·C에 CLAUDE.md · PROGRESS.md · SPEC 초안 원문을 그대로 실어 "한 글자도 바꾸지 않고" 생성하게 한다.

## 4. 결정 로그

- 결정은 `D<n>`으로 번호를 매기고 CLAUDE.md 표에 일자와 함께 적는다. 기획자님 확인 대기 결정은 "(세부 확인 대기)"를 붙이고 기본값으로 착수한다.
- SPEC 이탈은 숨기지 않는다. 검수가 이탈 항목별로 승인/불승인을 판정하고, 승인분은 SPEC 버전을 올려 반영(v1.0 → v1.1).
- 사용자가 명시적으로 거부한 안은 "다시 제안하지 말 것"으로 기록한다.

## 5. 검수 판정 형식 (jc-redteam 판정 라벨 + 빌드 검수 확장)

종합 판정 라벨은 `jc-redteam` SKILL.md §6의 3종을 그대로 쓴다(별도 어휘 금지). 아래 'SPEC 이탈'·'기획자 결정'·'실기 검수' 행은 코드 빌드 검수 전용 확장이다.

```
종합 판정: ✅ 결론 유지 | ⚠️ 조건부 보완 | 🔴 결론 재검토 — Critical N · Major N · Minor N
Major 항목: M-1 <현상 → 수정 지시(파일·함수·기대 결과)> …
SPEC 이탈: ①…⑨ 각각 승인/불승인
기획자 결정: (판정에 딸린 결정 항목 표)
실기 검수: (누가 어느 계정으로 무엇을 실기 확인할지)
```

- 검수는 독립 재현(테스트 재실행·빌드 바이트 대조·UI 경로 재현)을 근거로 한다. 스크린샷·수치 없는 판정은 판정이 아니다.
- 패치는 검수 결과를 사실로 받아들인다. 재검증에 시간을 쓰지 않고, 고친 뒤 영향 경로 게이트만 다시 돈다.

## 6. 게이트 실행 원칙

- 메인이 직접 실행한다. 서브에이전트 보고를 게이트 결과로 대체하지 않는다.
- 정적 캡처만으로 통과 처리 금지. 실렌더 게이트는 탭·화면·쓰기 경로 전수.
- 로컬 PC에서 도구가 없으면(npm·Playwright) 대체 스크립트(헤드리스 Chrome + DevTools 프로토콜 등)를 만들거나 클라우드 세션·CI로 넘긴다. 어느 쪽이었는지 보고에 명시.
- 패치 후 재검증: 코드를 고친 뒤 영향 경로의 게이트를 다시 돌린다. 저자가 만든 경로만 확인하는 것은 검증이 아니다.

## 7. 산출물 배치 규칙

- 원본은 `src/`(또는 `02_build/`)에만 고치고 빌드 산출물(`apps-script/index.html`·`preview/*.html`)은 빌드 스크립트로 생성한다.
- 문서: `docs/SPEC-v*.md`(정본) · `docs/DATA-CONTRACT.md` · `docs/code-brief-*.md` · `guide/`(비개발자 클릭 단위 가이드). 공유용 문서 기본 산출은 Claude Docs.
- 검수 리포트: `03_review/` 또는 `docs/review-*.md`.
- 실데이터·개인정보가 든 파일(`data/*.tsv`, 시트 URL)은 저장소 공개 여부를 확인하고 `.gitignore`·정적 검사로 감시한다.
