# 베뉴 DB 실데이터 레퍼런스 (venues-db)

**출처**: 베뉴파인더 도구(`베뉴파인더/_data/venues.json`, 견적이력 100건) + 베뉴파인더.html 내 `ALIAS`/`REGION`/`VENUE_SPECS` 마스터(정규화 로직 이식).
**생성일**: 2026-07-03
**생성 스크립트**: [build_venues_db.py(개발 워크스페이스 sprint-08/venue-data/ 소재 — 본 패키지 외부)](build_venues_db.py(개발 워크스페이스 sprint-08/venue-data/ 소재 — 본 패키지 외부)) (재실행 시 동일 결과 재현 가능)
**레코드 단위**: 베뉴(venue_name) × 홀(hall_name) 조합. 동일 베뉴+홀에 대한 복수 견적(다일자)은 1레코드로 그룹핑.
**필드 스키마**: canonical `_canonical/mice-estimate/references/venue-db.md` §1과 필드명을 최대한 맞췄으나 완전 1:1은 아니다 — 정확한 갭은 [integration-note.md(개발 워크스페이스 sprint-08/venue-data/ 소재 — 본 패키지 외부)](integration-note.md(개발 워크스페이스 sprint-08/venue-data/ 소재 — 본 패키지 외부)) §2 참조.

## 0. 데이터 읽는 법 (중요 — 반드시 먼저 읽을 것)

1. **`min_rental`/`max_rental_observed`는 대관료 단독 금액이 아니다.** 받은 견적의 총액(VAT 포함, 대관료+식음료+고정비+커피브레이크 등 포함)의 관측 범위다. `per_pax_rate`는 이 이유로 **전 레코드 `null`**(인당 순수 대관단가로 분리 불가 — 소스에 그런 필드가 없음).
2. **`max_capacity`는 해당 베뉴·홀에서 관측된 견적상 좌석수(seat) 최댓값**이다. 베뉴파인더 도구가 사용하는 '연회식 기준' 수치와 동일한 개념 — 극장식/클래스식 등 다른 배치의 수용인원은 이 데이터셋에 없다(도구 자체는 비율 추정을 적용하지만, 본 산출물은 추정치를 만들지 않고 원본 관측값만 담았다). 이벤트 형식이 다르면 실제 수용 가능 인원은 다를 수 있다.
3. **`venue_type_raw`는 "호텔" 또는 "유니크"뿐**이며 canonical 4분류(`5star`/`conference_center`/`convention_center`/`hotel_grade1`)로의 등급 매핑은 **수행하지 않았다** — 실제 성급이 소스에 없어 임의 판정 금지.
4. **`amenities`는 견적서의 `equip`(장비) 필드를 그대로 옮긴 것**이다 — LED, 빔프로젝터 등 자유텍스트이며 표준화된 부대시설 목록이 아니다.
5. **개인정보(담당자 연락처·이메일·고객사명)는 의도적으로 전부 제외**했다 — 베뉴파인더 README의 비공개 경고 준수. `client_count`(고객사 수)만 익명 집계로 남김.
6. **표본이 작고 편중**되어 있다 — 베뉴당 관측 견적 1~16건, 2026년 4~5월 견적/6~8월 행사 시점, 소수 클라이언트向 견적 중심. 시장 평균가로 일반화 금지, 참고 스케일 감으로만 사용.
7. **null/– 표기는 원본에 없는 값**이다. 임의로 채우지 않았다.

## 1. 요약

- 총 레코드(베뉴×홀): **25건** (원본 견적이력 100건 → 23개 베뉴+홀 그룹 + FKI타워 스펙전용 2건)
- 고유 베뉴 수: **12개**
- 지역: 강남권, 도심권, 여의도권, 마포권, 용산권
- 출처별: 견적이력_실데이터 23건, 스펙_추정 2건

## 4. mice-estimate 사용 가이드

### 4.1 대관료(s1) 라인아이템 참고 시

- calc_estimate의 `venueRental` 직접입력에 `min_rental`/`max_rental_observed`를 **그대로 대입하지 말 것** — F&B·고정비 포함 총액이다. 순수 대관료가 필요하면 베뉴 담당자에게 별도 견적 요청.
- 참고용 시장 스케일 감: 예) 200명 규모 강남권 대관 시 관측된 견적 총액이 26백만~51백만원대(JW메리어트·조선팰리스·인터컨티넨탈 등)였다.

### 4.2 수용인원 검증(capacity check) 시

- `target`(참석인원)이 `max_capacity`를 초과하는지 sanity check로 사용. 단, 이 수치는 견적상 관측된 좌석수이지 베뉴 공식 정원이 아닐 수 있음에 유의.
- 이벤트 형식(컨퍼런스형 vs 만찬형)에 따라 실제 수용 가능 인원이 달라진다 — 형식이 다르면 베뉴에 재확인 권고.

### 4.3 venue_id 룩업 연동

- 상세 통합 방법(스키마 갭·lookup_venue 구현 제안)은 [integration-note.md(개발 워크스페이스 sprint-08/venue-data/ 소재 — 본 패키지 외부)](integration-note.md(개발 워크스페이스 sprint-08/venue-data/ 소재 — 본 패키지 외부)) 참조.

## 5. 알려진 한계 (Do Not Invent 원칙 준수)

| 항목 | 상태 |
|---|---|
| 대관료 단독 금액(per_pax_rate, 순수 min_rental) | ❌ 소스에 없음. 견적 총액(F&B 포함)만 존재 → per_pax_rate 전 레코드 null |
| 좌석배치별(극장식/클래스식) 수용인원 | ❌ 이 산출물에는 없음(추정치를 만들지 않기 위해 관측값 1종만 유지) |
| 베뉴 정원(진짜 최대 캐파) | ⚠️ 견적이력상 관측된 좌석수 최댓값으로 근사 — 실제 정원과 다를 수 있음 |
| venue_type 성급 등급 | ❌ "호텔"/"유니크" 원본 분류만 존재, 5star 등 등급 미검증 |
| amenities 표준 목록 | ⚠️ equip 필드 자유텍스트 그대로, 구조화 안 됨 |
| 담당자 연락처·고객사명 | ❌ 의도적 제외 (개인정보, 베뉴파인더 README 경고 준수) |
| 표본 대표성 | ⚠️ 특정 시기·소수 클라이언트向 견적 중심 — 시장 전체 평균 아님 |
