# 커뮤니케이션 양식 — 리멤버 Slack·메일 맥락

구 커뮤니케이션 양식 스킬의 4종(3P·뉴스레터·FAQ·일반 보고)을 이관해 리멤버 운영에 맞게 응축했다(v1.3.0에서 뉴스레터·프로젝트/리더십 업데이트·3P 세부 규칙 보강).

모든 양식의 기본 산출은 복사용 초안이다. 초안 → 사용자 검토 → 발송(사용자가 직접 붙여넣거나, 명시 승인 후). 발주처·외부용은 발송 전 `jc-redteam` Quick Strike 권장. **Slack에는 최종본만** — 작성 근거·버전 비교·검토 메모는 붙이지 않고 로컬 md로 분리한다.

## 0. 톤 분기

| | 내부(팀·사업실) | 대외(발주처·참가자·협력사) |
|---|---|---|
| 문체 | Slack 해요체 허용, 핵심만 | 합니다체, 정중·사실 위주·완결 문장 |
| 리스크·문제 | 원인·내부 사정 솔직 | 영향 + 대응책 중심, 책임 공방 배제 |
| 금액·마진·내부 일정 | 기재 가능 | 비노출("별도 공유 예정") |
| 실명·평가 | 허용 | 역할명("발주처 담당자"), 완곡 |
| 모호할 때 | — | 보수적(외부) 톤으로 |

명의는 리멤버 MICE비즈팀, 발주처·담당자·행사는 `{발주처}`·`{발주처 담당자}`·`{행사명}`·`{행사 ID}` 슬롯. 예시의 고객사는 가명(A사)이다.

## 0-1. 양식 고르기 · 공통 원칙

| 요청 | 양식 | 주 독자 | 분량 |
|---|---|---|---|
| 제도·프로세스 변경, 참가자 안내 | §1 공지 · 안내문 | 사업실 / 참가자·발주처 | 5~8줄 |
| 행사·팀의 한 주 진척 | §2 3P | 발주처·팀·실장 | 3줄(30~60초) |
| 정기 상태 신호(정상/주의/위험) | §3 상태 보고 | 발주처·경영진 | 6줄 |
| 현장 장애·사고·중대 차질 | §4 인시던트 보고 | 팀 → 발주처 | 1보 3줄 |
| 이해관계자 묶음에 마일스톤 경과 | §5 프로젝트 업데이트 | 발주처+협력사+팀 | 6항 |
| 의사결정자에게 결론·필요 결정 | §6 리더십·경영진 업데이트 | 실장·경영진 | 30~60초 |
| 여러 행사·팀 소식 묶음, 행사 안내 | §7 뉴스레터 · 소식지 | 사업실 / 참가자·파트너 | 불릿 20~25 |
| 발주처 안내·지연 안내 | §8 발주처 메일 | 발주처 담당자 | — |
| 반복 문의 표준 응답 | §9 FAQ | 참가자·스폰서·발주처 | 문항당 1~2문장 |

- 금요일 사업실 퍼포먼스 리포트는 `weekly-brief.md`, 보고 덱(PPTX)은 `jc-pptx`, 결과보고서는 `mice-aftermath`.
- 두괄식(첫 줄 = 결론), 능동태, 숫자에 단위, 근거 링크. 대상·목적(알림 / 결정 요청 / 수습 / 경과)·매체(Slack / 메일)가 비면 기본값(내부·Slack)으로 쓰고 한 줄로 밝힌다.
- 근거 수집은 도구가 있을 때만(Slack 반응·답글 많은 글, 상태 보드, 메일 스레드, 드라이브 문서, 캘린더 큰 일정). 없으면 사용자에게 항목을 받아 양식으로 정형화한다.

## 1. 공지 · 안내문

내부 공지 (사업실·채널, 해요체 허용):
```
[공지] {제목} — {시행일}
{한 줄 결론: 무엇이 언제부터 어떻게 바뀝니다.}
- 대상: {마켓데이터사업실 · 광고사업실}
- 바뀌는 것: 1) … 2) … 3)
- 안 바뀌는 것: …
- 문의: MICE비즈팀 @{팀장} · 상세: (캔버스/구글독 링크)
```
- 다른 팀 방식을 규정하는 문장 금지("각 팀 기준을 따릅니다"로 끝).
- 시행일 전 D-7·D-1 리마인드는 별도 짧은 메시지.

대외 안내문 (참가자·발주처, 합니다체):
```
[{행사명}] {안내 제목}
{핵심 한 문장: 무엇을 언제까지 해 주시면 됩니다 / 무엇이 바뀌었습니다.}
- 일시·장소: {일시} · {장소}
- 대상·준비물: …
- 해 주실 일: {무엇을 · 언제까지 · 어디서(링크)}
문의: 리멤버 MICE비즈팀 {담당 메일}
```
- 변경 안내는 무엇이 → 어떻게 → 받는 사람이 할 일 순. 사과는 한 문장, 내부 사정은 쓰지 않는다.

## 2. 3P 주간 업데이트 (Progress / Plans / Problems)

```
📌 {행사 ID 또는 팀} 주간 업데이트 ({기간})
Progress: {지난주 진척 1~3문장, 숫자}
Plans: {이번 주 1~3문장}
Problems: {막힌 것 + 필요한 결정/지원. 없으면 "없음"}
```
- 30~60초 분량. 사실 위주, 장황한 산문 금지. 포맷은 3줄 고정(다른 칸 추가 금지), 이모지는 행사 성격에 맞게 1개.
- 칸 정의: Progress = 지난 1주 **완료된 일**(확정·오픈·체결·송출), Plans = 다음 1주 최우선 항목, Problems = 속도를 늦추는 것(인력, 발주처 결정 지연, 협력사 단가, 베뉴 변경, 섭외 무산). 수집 기간은 Progress·Problems 지난 1주~오늘, Plans 오늘~다음 1주.
- 무엇에 대한 3P인지(행사 ID·팀) 먼저 정한다. 맥락으로도 모르면 한 번 묻는다.
- 실장·경영진 보고용은 Problems에 "요청 사항(결정 필요)"을 반드시 붙인다.

단위가 클수록 덜 쪼갠다:

| 단위 | 항목 입도 | Progress 예 |
|---|---|---|
| 행사 1건 | 업무 | "연사 12명 확정(목표 14명 중 86%) · 등록 오픈 첫 주 320명(목표 대비 64%)" |
| 팀(MICE비즈팀) | 행사 | "킥오프 2건 완료 · 현장 1건 성료 · 정산 2건 진행" |
| 사업실·경영진 | 포트폴리오 | "이번 달 수주 2건 확정 · 4분기 파이프라인 5건" |

여러 행사를 한 글에 묶을 때는 줄마다 행사 ID 접두. Problems는 독자에 따라 갈라 쓴다:
- 대외(발주처·협력사): "잔여 연사 2명 일정이 미확정입니다. 발주처 확인을 기다리고 있으며, 6/14까지 미확정 시 대체 섭외안을 가동합니다."
- 내부(팀·실장): "발주처 컨펌이 3주째 밀려 연사 확정이 안 돼요. 이대로면 인쇄물 마감(6/20)도 위험 — 실장님이 발주처에 기한 요청 필요."

## 3. 상태 보고 (발주처·경영진)

```
■ {행사명} 상태 보고 ({날짜} 기준)
한 줄 요약: [정상 / 주의 / 위험] + 핵심 한 문장
- 전체 진행률: {N%} (마일스톤 {X/Y})
- 이번 주 주요 진척: {2~3개}
- 다음 주 핵심: {2~3개}
- 주의/리스크: {영향 + 대응. 없으면 "특이사항 없음"}
- 의사결정 요청: {컨펌 필요 항목, 없으면 생략}
```
- 상태 신호는 3단계만. **위험**에는 대응책과 필요한 지원을 반드시 같이 쓴다.

## 4. 인시던트 보고 (현장 장애·사고·중대 차질)

```
[인시던트] {행사 ID} · {발생 시각} · {심각도: 경미/중대/치명}
- 무엇이: {사실만. 추측·책임 단정 금지}
- 영향: {참가자·프로그램·비용}
- 조치: {완료 / 진행 중 / 예정 — 담당·시각}
- 발주처 안내: {했음/예정 — 누가 언제}
- 후속: {원인 파악·재발 방지 — 결과보고서 반영}
```
속도와 사실 정확성이 우선. 1차 보고는 10분 내 3줄이라도 먼저:
```
[인시던트 1보] {행사 ID} · {시각}
{무슨 일} · {영향} · 지금 {대응 중인 것} — 다음 업데이트 {시각}
```
- 대외 보고는 사실·대응·사과 한 문장. 내부 책임 소재는 빼고, 원인·경위는 내부 보관본에 솔직히.
- 금액·법적 책임·환불 약속은 책임자·발주처 확인 전에는 쓰지 않는다. 재발 방지가 미확정이면 "원인 분석 중".

## 5. 프로젝트 업데이트 (마일스톤 경과)

```
■ {행사명} 프로젝트 업데이트 ({기간})
1) 개요: {현재 단계 — 기획/준비/실행/마감} · {한 줄 요약}
2) 이번 기간 완료: {확정·산출 사항}
3) 진행 중: {돌고 있는 작업 · 담당}
4) 예정: {다가오는 마일스톤 · 날짜}
5) 이슈·리스크: {영향 + 대응}
6) 협조 요청: {발주처: … / 협력사: … / 팀: …} (없으면 생략)
```
- 발주처+협력사+팀 묶음에 보내는 경과 공유. 3P(1주·3줄 고정)보다 길고 서술적이어도 된다.
- 내부용은 단계에 S1~S7(`protocol.md §2`)을 함께 적고, 대외용은 합니다체·금액·마진·내부 일정 비노출.

## 6. 리더십 · 경영진 업데이트

```
■ {행사명 또는 팀} 업데이트 — 실장·경영진 ({날짜})
핵심 메시지: {지금 가장 알아야 할 것 1문장}
- 성과·임팩트: {수치 2~3개 — 수주·쇼업·리드·금액(억)}
- 리스크·이슈: {의사결정자가 알아야 할 것 + 영향도}
- **필요한 결정·지원: {무엇을 · 언제까지 · 누가}**
- 전망: {다음 달·다음 행사 한 줄} (선택)
```
- 30~60초 안에 읽히게, 실무 디테일 최소화, 필요한 결정은 굵게. 나쁜 소식도 숨기지 않는다.
- 상태 보고(§3)는 진행률·마일스톤 중심의 정기 신호, 이 양식은 결론·임팩트·필요 결정 중심. 금액 단위는 `weekly-brief.md`와 같이 억(소수 둘째 자리).

## 7. 행사 뉴스레터 · 소식지

| | 내부 소식지 (사업실·팀) | 대외 행사 뉴스레터 (참가자·발주처·파트너) |
|---|---|---|
| 톤 | 해요체, "우리" 시점("~를 오픈했어요") | 합니다체, 자축·내부 평가 절제 |
| 담는 것 | 수주·성료·목표 달성, 제도 변화, 팀장·실장 공지 | 행사 안내·프로그램·연사·등록 |
| 금액·내부 일정 | 기재 가능 | 비노출, 성과는 공개 가능한 사실·수치만 |
| CTA | 관련 스레드·문서 링크 | 등록·신청 링크 + 마감일 + 문의처 |
| 주기 | 월 1회 기본(지난 1주~1개월 소식) | 행사 일정에 맞춰(등록 오픈·마감 임박·사후 감사), 횟수는 발주처와 합의 |

```
:loudspeaker: 공지
- {공지 1~3개}
:dart: 행사 운영
- 준비 중: {행사명} 등록 오픈 첫 주 320명(목표 대비 64%)
- 진행 중: {행사명} 리허설 완료, D-7 점검만 남음
- 종료·결산: {행사명} 성료 — 쇼업 34 / 목표 30
:pushpin: 팀장·실장 메시지 (내부만)
:calendar: 다가오는 행사
- {행사명} — {일시} · {장소} · [사전등록 링크] {마감일}까지
```
- 불릿 20~25개, 불릿당 1~2문장. 섹션은 비슷한 것끼리 묶는다(준비 중 / 진행 중 / 종료·결산, 또는 대외 / 내부).
- 링크는 표시 텍스트로 감싸 건다. 길면 캔버스로 올리고(`canvas-rules.md`) 채널에는 3줄 요약 + 캔버스 링크.
- 넣을 것: 다수에 영향, 마일스톤(수주·성료·목표 달성), 외부 노출(기사). 뺄 것: 단일 행사 세부(→ §2 3P), 소수만 관련된 일, 이미 공지된 중복.

- {항목 1: 일정·장소·인원 등 사실}

- {요청·확인 사항: 무엇을 언제까지}

- 지연 안내는 사실 → 영향 → 대안 → 새 기한 순. 사과는 한 문장.

## 9. FAQ (참가자·스폰서·발주처)

```
[{대상}]
- 질문: {1문장}
- 답변: {1~2문장. 확정 사항 근거. 미확정은 "확정 후 안내"}
```
- 대상 그룹(참가자 / 발주처 / 스폰서)부터 정한다 — 질문 풀과 톤이 다르다. 한 사람의 질문이 아니라 여러 명이 반복한 질문만.
- 일정·금액·계약·환불은 발주처/책임자 컨펌 없이 추측 답변 금지. 컨펌 필요 항목은 플래그.
- 출처(운영 안내·공지·메일) 링크. 내부 정리본에는 현재 상태·담당·대기 일수를 함께 적는다.

## 10. 팀 내부 짧은 글

- 킥오프 회의록 공유: "[킥오프] {행사 ID} 회의록 (링크) — 결정 3줄 · 액션 N건(담당·기한)".
- 결정 기록: `[결정] {무엇을} — {누가} · {언제}` 한 줄.
- 요청: 첫 줄에 원하는 것 + 기한, 배경은 그 아래.
